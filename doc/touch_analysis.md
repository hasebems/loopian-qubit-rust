# タッチ解析（複数の電極から 1 つのタッチを求め、演奏情報を取り出す） 設計書

2026-11-08 書き始め。

## 1. 背景と目的

### 1.1 本書の範囲

タッチの処理は、次の 2 段に分かれる。

| 段 | 扱うもの | 実装 | 設計書 |
|---|---|---|---|
| 信号処理 | 電極 1 つずつ。ノイズ除去・基準値・noise_floor を扱い、電極毎の output を出す | `crates/touch_algo` の `electrode.rs`（`ElectrodeSignal`） | `doc/touch_baseline.md` |
| 解析（本書） | 複数の電極の output から 1 つのタッチを求め、そこから演奏情報（ノート・ベロシティ・ビブラートなど）を取り出す | `crates/touch_algo` の `touch.rs`（`TouchTracker`: depth・position）と `playinfo.rs`（`PlayInfo`: 演奏情報）。2026-11-08 に `src/touch/qtouch.rs`（`QubitTouch`）から移して分けた（§5.6・§7） | 本書 |

入口は `doc/touch_baseline.md` §3.9 の受け渡し（`ElectrodeSignal::process()` の output を `TouchTracker::set_value()` で渡す。分ける前は `QubitTouch::set_value()`）である。

### 1.2 目標

1. **（第一の目標）1 本の指のタッチを、1 つのタッチとして求める。そのタッチは depth と position の 2 つの情報を持つ**（§3）
2. 求めたタッチから演奏情報を取り出す（ノート・ベロシティ・ビブラートなど。§4、後で検討する）
3. 複数の指（最大 `MAX_TOUCH_POINTS` 点）への拡張（後で検討する）。決め打ちの距離（初めは 6 電極、調整する）以内の指は分けない（§3.7、2026-11-08 決定）

## 2. 用語

| 用語 | 意味 |
|---|---|
| 電極 | タッチセンサの 1 つの電極（electrode）。AT42QT1070 の 1 チャンネルに当たる。`touch_algo` の output が電極毎に 1 つある。データシート・`doc/touch_baseline.md`・コードの多くでは key（キー）と呼んでいるが、本書では電極と呼ぶ |
| output | `touch_algo` が電極毎に出す値。`delta − noise_floor`（0 未満は 0）。未タッチで 0、触れると正（`doc/touch_baseline.md` §2） |
| タッチ | 1 本の指が触れていることを表すもの。隣り合う複数の電極の output から 1 つ求める。**タッチは指 1 本の単位だけに使い、電極 1 つの反応はタッチと呼ばない**（「電極が反応する」と言う）（2026-11-08 決定） |
| depth | タッチの深さ。指がどれだけ強く・広く触れているかを表す量（§3.2） |
| position | タッチの位置。電極番号を単位とする実数（電極間の位置も表す）（§3.3） |

## 3. 第一の目標: 1 本の指のタッチ

### 3.1 考え方

1 本の指は、電極の幅より広いので、隣り合う複数の電極（2〜3 個程度）にまたがって触れる。電極毎の output を個別に見るのではなく、まとめて **1 つのタッチ** とし、そのタッチを次の 2 つの量で表す。

- **depth**: どれだけ触れているか（§3.2）
- **position**: どこに触れているか（§3.3）

演奏情報（§4）は、この 2 つの量とその時間変化から取り出す。電極毎の output は、ここから先の処理には直接使わない。

### 3.2 depth（2026-11-08 決定）

**1 本の指とみなした電極の output を、すべて足したもの。**

```
depth = Σ output[k]    （k は 1 本の指とみなした電極）
```

- 指の押しつけの強さと、触れている面積の両方を含む量になる
- 現状の強度（intensity、§5）と同じ考え方。違いは足す電極の範囲で、現状は山の前後 3 電極（計 7 電極）と決め打ちにしている。どの電極を 1 本の指とみなすかは §3.4 で決める
- **depth は output をそのまま足した線形の量とし、テーブルなどで変換しない（2026-11-12 決定）**。検討して取り下げた案:
    - 各電極の output を、大きい値ほど大きくなるテーブルで変換してから足す: 電極の真上と中間で depth の違いを補正するつもりだった。ただし、真上と中間で output の合計がどう違うかは確かめていない。合計が同じなら、変換によってかえって真上の depth のほうが大きくなる（例: x² なら 6, 6 → 72、12, 0 → 144）
    - 足した後の depth を強調する: 触れる速さを取るためのもの。depth は有無の判定（§3.5）にも使うので、タッチの層では線形のままにする。強調が要るなら、演奏情報の層で速さを求めるとき（§4.2）に考える

### 3.3 position（2026-11-08 決定）

**1 本の指とみなした電極の output の重心。** 現状（§5）と同じ。

```
position = Σ (k × output[k]) / depth
```

- 単位は電極番号で、電極の間の位置も実数で表す
- 足す電極は depth と同じ（§3.4）
- リングのつなぎ目（電極 95 と 0 の間）の扱いは §3.6

### 3.4 1 本の指とみなす電極の範囲（2026-11-13 方針）

**output が k より大きい電極が続く区間を、1 つの候補とする。depth・position は、その区間の電極の output をそのまま使って求める。k は設定値にする（初めは 2〜3）。**

まずはシンプルなルールから始める（2026-11-13）。

- 区間: 隣り合う電極の output が続けて k を超えている範囲。k 以下の電極で区切る。今の「山を探して前後 3 電極（計 7 電極）の窓」と「近い候補の統合」（§5.3 の 1〜2.5）の代わりになる
- k は区間を決めるためだけに使う。depth（§3.2）と position（§3.3）は、区間の中の output をそのまま足して求める（k を引いたりしない）
- k を 0 にしない理由: 2 本の指の間や区間の端に 1〜2 の小さな output が残ると、離れた指がつながったり、ノイズの電極が区間に入って position がずれたりするため
- 良くなる点:
    - 窓で切れないので、指を寝かせて幅広く触れても depth が欠けない
    - 平らな頂上（§6.1 の 1）や、1 本の指で山が 2 つできる場合も、区間が 1 つなら 1 つの候補になる。近い候補の統合はほぼ要らない
    - 区間を見つけた時点で depth も求まるので、depth で絞ってから `MAX_TOUCH_POINTS` 個にできる。ノイズの小さな山が候補の枠を埋めない
- 代わりに起きること: 端の電極が k を超えた瞬間に区間に入るので、position が少し跳ねる（大きさは k × 中心からの距離 / depth 程度。k = 2、距離 2、depth 50 なら 0.08 電極）。立ち上がりの始めや離す直前は depth が小さいので、端の電極が抜けた分の割合が大きい。k は大きくしすぎない

未決:

- k の値と置き場所（`touch.rs` 先頭の定数か、`electrode` の `Params` のような構造体か）。qubit_etude から変えられるようにすると、記録を見ながら決めやすい
- 幅が §3.7 の距離（6 電極）を大きく超える区間を、谷で分けるか。2 本の指の間が k 以下にならないと、1 本になって position が真ん中に出る
- リングで、全部の電極が k を超えたとき（手のひらで触れたなど）。リングでは k 以下の電極から走査を始めれば、つなぎ目をまたぐ区間も 1 つになるが、k 以下の電極が無いと区間が 1 周になる
- 記録（`.qlog`）で確かめること: 区間の幅の分布、触れていない所に残る k を超える電極の数、2 本の指の間が k 以下になっているか

### 3.5 タッチの有無の判定（2026-11-13 方針）

**指の有無は depth で決める。指の検出と Note On/Off は連動させない（Note On/Off は §4.2）。**

まずはシンプルなルールから始める（2026-11-13）。

- **触れ始め**: 区間（§3.4）の depth が ON のしきい値を超え、近くに追跡中の指が無ければ、新しい指にする（`Started`）。山の電極 1 つの output では決めない。指が 2 つの電極のちょうど間にあると output が割れて（例: 6, 6）山が小さくなるため、山の値で決める今の実装では、触れる場所で感度が変わる（§6.2 の 1）
- **続き**: 追跡中の指の近くに区間があれば、depth によらず同じ指が続いているとする（`Followed`）。区間は output > k で決まるので、OFF のしきい値は k の所にあることになる。ON のしきい値より低いので、ヒステリシスになる
- **途切れ**: 近くに区間が無い周期は、今と同じく `RELEASE_WAITING_TIME` の間だけ指を保持し、続いたら離れたとする（`Released`）。保持している周期（`Track::None` で `is_touched()` が true）の depth・position は、最後に見つけた周期の値のまま。その意味は「この周期は指を見つけられなかった」で、演奏情報の層はこの周期の depth を速さ・遅さの履歴に入れない（§4.2）
- 区間で探せば、見つけられない周期は、近くの output がほぼ k 以下、つまり depth が本当にほぼ 0 の周期だけになる。ゆっくり離すときの depth の下がり方は、区間が見つかっている間（`Followed` の間）にすべて見える
- 検出のしきい値は低めにする。演奏情報の層は depth の立ち上がりから触れる速さを求める（§4.2）ので、立ち上がりの始めから depth を渡したい。ON のしきい値を高くしてチャタリングを抑える必要は、§4.2 で指の検出とノートを切り離すので小さい
- 同じ指を同じ TouchPoint に保つ仕組みは、タッチの層に残す。検出が途切れて Released → Started になると、演奏情報の層からは別の指に見え、速さの計測や位置の履歴がやり直しになるため。ノートを遅らせても、これは要る

ヒステリシス: 前の状態（触れている / いない）に応じて、しきい値を 2 つ使い分けること。触れていないときは ON のしきい値を超えたら触れたとし、触れているときは OFF のしきい値（ON より低い）を下回るまで触れたままとする。値そのものには手を加えないので、平滑化と違って遅れない。今の `RELEASE_WAITING_TIME` は、同じ揺れを時間で待って抑えるやり方にあたる

検討して取り下げた案（2026-11-13）:

- 保持している周期にも、最後の position の窓で output を足し直して depth を渡す: タッチの層の中に、depth の求め方が 2 通り（候補から / 例外の窓から）できてしまい、どちらで求めた値かで depth の意味が変わるため。区間で探して、見つけられない周期そのものを減らすほうを選んだ
- その延長として考えた「保持中の depth がほぼ 0 ならすぐ離れたとし、残っていれば長めに保持する」（速く離せばすぐ終わり、ゆっくり離せば長く保つ）も、同じ理由で今は入れない。区間で探せば、ゆっくり離す間は `Followed` が続くので、近い効き目になる

未決:

- ON のしきい値の値。記録（`.qlog`）を `replay_algo` に通し、触れていないときの depth の最大と、軽く触れたときの depth を見て決める。depth は山の 2〜3 倍程度になるはずなので、今の 8 はそのまま使えない
- `RELEASE_WAITING_TIME`（今は 5 周期）を短くするか。区間で探せば途切れは減るので、短くして Note Off の遅れ（今は 50〜60ms）を減らせる見込み。§4.2 の「離すときの遅さ」と一緒に決める

### 3.6 リングのつなぎ目（2026-11-08 方針）

**depth・position を求めることと、それを演奏情報にすることを分ける。**

- **depth・position**: つなぎ目をまたいでも、なるべく正しく出す。つなぎ目の上の指も、ほかの場所の指と同じように 1 本のタッチとして、同じ精度の depth・position を出す（position は 0 以上 96 未満に巡回させる）。この段階では、つなぎ目だからといって特別な処理（切り捨て・別のタッチにする等）はしない
- **演奏情報**: つなぎ目をまたいだときに Vibrato・Move（ノートの移動）などをどう扱うかは、演奏情報の側で特別な処理として決める（§4.1）
- 今の実装（§6.1 の 3 の修正）は、この方針の depth・position の側にあたる。リングでない構成（etude・no_pca9544）には、つなぎ目は無い

### 3.7 近い複数の指（2026-11-08 決定）

**ある距離以内にある複数の指は、分けて認識しない。1 本のタッチとして扱う。その距離は決め打ちの定数とし、調整する（初めの値は 6 電極）。**

- 指を電極の並びに沿って寝かせて触れれば、1 本の指でもいくらでも幅広く触れられる。これと、近くに並べた複数の指を、このセンサで見分けることはできない
- そのため、1 本の指とみなす範囲（§3.4）は決め打ちでよい。範囲の中に山が複数あっても、1 本のタッチにまとめる
- 複数の指を分けて認識するのは、その距離より離れているときだけ（目標 3）。距離は演奏して調整する
- これにより、§6.1 の 2 の「4〜6 電極離れた 2 本の指」と §6.2 の 3 の「2 本の指が近づいたときの入れ替わり」は、扱わなくてよい問題になる（その距離以内に近づいたら 1 本になる）
- ~~今の実装との違い（まだ直していない）~~: 今は、position の差が `CANDIDATE_MERGE_RANGE`（1.6 電極）以内の候補だけをまとめるので、1.6 電極より離れた山は別のタッチになる。§3.4 で範囲を決めるときに、まとめる距離をこの定数に合わせる
    - 2026-11-13: 候補を区間にした（§3.4）ので、`CANDIDATE_MERGE_RANGE` と統合の処理は無くなった。今は、間に `SEGMENT_THRESHOLD` 以下の電極があれば、近くても別のタッチになる（例: output 20, 5, 30 は電極 2 つ離れた 2 つのタッチ）。決め打ちの距離でまとめるかは、§3.4 の未決（谷で分けるか）と一緒に決める

#### 3.7.1 1 本と 2 本の境目の往復（2026-11-13 見つけた）

qubit_etude で、1 本と 2 本の判断の境目で、派手に往復が起きるのをユーザーが見た。区間（§3.4）で探すようにしてから、§3.7 の距離でまとめる処理が無くなったため、間に `SEGMENT_THRESHOLD` 以下の電極が 1 つでもあれば、近くても 2 本に分かれる。

`touch_algo` に output を与えて確かめた（電極 3〜4 と 6〜7 に 2 本の指、間の電極 5 が k をまたいで 8 と 4 を行き来する）:

- 区間が 1 つ（position 4.86）と 2 つ（3.62・6.38）を行き来する
- 1 本目の position が 1 本以上跳ぶので、区間が変わる度に Move が往復する（22 ↔ 21）
- 2 本目は、揺れが保持（5 周期）より速ければ保持されたまま続き、遅ければ Note Off・Note On を繰り返す。ID が入れ替わることもありうる

#### 3.7.2 決め打ちの距離とヒステリシス（2026-11-13 方針、同日実装）

**タッチの層で、近い区間を決め打ちの距離でまとめる。まとめる距離と分ける距離に差をつけて、ヒステリシスにする。**

- 隣り合う区間の position の差が距離 D 以内なら、1 つの候補にまとめる。まとめた候補の depth・position は、左の区間の先頭から右の区間の終わりまで（間の k 以下の電極も含めて）の output から求め直す
- D は、前の周期の指の数で変える:
    - その範囲（2 つの区間の position の間、少し広げる）に、前の周期の指が 1 本だけあった（今まで 1 本だった）: D = 分ける距離（`SPLIT_DISTANCE`、初めは 7 電極）。これより離れるまで、1 本のまま
    - 2 本以上あった（今まで 2 本だった）、または 1 本も無かった（新しく触れた）: D = まとめる距離（`MERGE_DISTANCE`。初めは §3.7 の初めの値の 6 電極としたが、区間で探すと遠すぎたので、2026-11-13 に 4 電極にした）

### 3.8 時間は実時間で数える（2026-11-13 決定）

**タッチの層と演奏情報の層の時間は、解析の周期の数ではなく、実時間（µs）で数える。** 解析が 10ms 毎に呼ばれなくても（96 キーでスキャンが 10ms を超える、`hw96_check.md` §2.1）、時間の感覚がずれないようにする。変わるのは時間の分解能だけになる。

- `TouchTracker::update` に今の時刻（µs）を渡す。`PlayInfo` は、`TouchTracker` が持つ最後の時刻を使う。時刻は u32 の µs（約 71 分で一周）で、差は `wrapping_sub` で求める
- 実時間にするもの:
    - `touch.rs`: 指を保持する時間（`RELEASE_WAITING_TIME` 5 周期 → `RELEASE_WAITING_US` 50ms。最後に見つけてから 50ms を超えたら離れたとする。10ms 毎なら今と同じ）
    - `playinfo.rs`: Note On までの経過（周期の数 → µs）、上限の時間（`NOTE_ON_TIMEOUT_CYCLES` 30 → `NOTE_ON_TIMEOUT_US` 300ms）、ベロシティの補間（経過の µs で線形）。ビブラートの周波数（`TOUCH_SAMPLE_PERIOD_SEC` 10ms の決め打ち → 位置の履歴の各サンプルの時刻から、履歴の長さを求める）
- サンプルの数のままにするもの: `electrode` の中央値フィルタ（3 サンプル）と平滑化（`smooth_samples`）。ノイズ除去の効き方はサンプルの数で決まる性質のため。`electrode` の時間のパラメータ（基準値の更新の間隔・初期取得・noise_floor の計測など）は、もともと時刻で数えている
- 10ms 毎に呼ばれる限り、出るイベントは今と同じになるはず。記録を `replay_algo` に通して確かめる

実装（2026-11-13）:

- `TouchTracker::update(now_us)`・`TouchTracker::now_us()`。`TouchPoint` は周期の数（`touching_time`・`no_update_time`）の代わりに、最後に見つけた時刻（`last_seen_us`）を持ち、`now_us − last_seen_us > RELEASE_WAITING_US`（50ms）で離れたとする。`TouchPoint::touching_time()` は使われていなかったので消した
- `PlayInfo`: `Voice` は指を検出した時刻（`onset_start_us`）を持ち、経過は時刻の差。`NOTE_ON_TIMEOUT_US`（300ms）、`onset_velocity(経過の µs)`。位置の履歴に各サンプルの時刻（`history_time_us`）を持たせ、ビブラートの周波数は履歴の最も古いサンプルから最も新しいサンプルまでの実時間で求める（`TOUCH_SAMPLE_PERIOD_SEC` は消した）

### 4.1 リングのつなぎ目での扱い（2026-11-08 決定）

§3.6 のとおり、depth・position はつなぎ目をまたいでも正しく出ているものとし、つなぎ目をまたいだときの扱いは、演奏情報に変換するときのルールとして決める。

- **Move（ノートの移動）**: つなぎ目をまたぐ Move はしない。95 → 0 も 0 → 95 もしない（Violin では電極 2 つで 1 ノートなので、47 → 0 と 0 → 47）
- **Vibrato**: position が 95 以上（電極 95 と電極 0 の間）では行わない
- 他の演奏情報（§4 で決めるもの）も、つなぎ目をまたぐときの扱いを一緒に決める

実装（2026-11-08。§5.6 の演奏情報の層）:

- Move とつなぎ目: ノートが変わったとき、ノートの番号が半周（ノートの数 / 2）より大きく変わったら、つなぎ目を越えたとして `cross_seam`、そうでなければ `move_note` を呼ぶ。番号で見るので、position が 95.3 → 95.7（ノート 95 → 0）のように、position はつなぎ目を越えていなくてもノートが越えた場合も含む
- Vibrato: どれかの指の position が電極数 − 1 以上（96 電極では 95 以上）の間は、検出した値を出さない（CC を送らず、`vibrato()` も前の値のまま）。リングの構成だけ

細かい扱い（2026-11-08 決定）:

1. **つなぎ目を越えて進んだ指**（例: 95 で触れ始めて 0・1・2 と動いた）: Move せず、前のノートの Note Off（KeyOff）と、越えた先のノートの Note On を出す
    - Move は「次のノートの Note On を出して、前のノートの Note Off（MOVED）を出す」ことなので、出るイベントは今の Move とほとんど同じでもよい。ただし、後で Move に何か（Move らしい処理）を足すことがあるので、つなぎ目を越えたときの処理は Move とは別の関数にしておく
    - Note Off は `STATUS_NOTE_OFF`（Move の `STATUS_NOTE_MOVED` ではない）。順番は Note Off → Note On
    - タッチ（TouchPoint）は同じものが続く。depth・position は §3.6 のとおり途切れずに出し、変わるのは演奏情報への変換だけ
2. **position が 95.5 以上で新しく触れたとき**: ノートは 0（四捨五入で 96 になったら巡回させる。今の実装のまま）
3. **Vibrato**: position が 95 以上の間は、検出した値を出さない。位置の履歴にはそのまま入れる

### 4.2 Note On / Note Off を出す時刻（2026-11-12 決定、2026-11-13 追記）

**指を検出しても、すぐには Note On を出さない。遅れが気にならない程度の時間を待ち、触れる速さ（depth の立ち上がり）を測ってから出す。Note Off も同じく、指の検出とは連動させず、離すときの遅さを求める。**

- 速さを測るのに使う depth は、線形の depth（§3.2）。強調などの変換が要るなら、速さを測った後、演奏情報の層でかける

- **Note On**: 指を検出してから depth の立ち上がりを見て、触れる速さを求め、ベロシティにする。今は検出した最初の周期で Note On を出すので、depth がほとんど立ち上がっておらず、ベロシティは触れ方によらずほぼ一定になっている（§6.3 の 2）
- **Note Off**: 離すときの遅さ（depth の下がり方）を検出する。速く離したか、ゆっくり離したかを区別したい
- **チャタリングへの効き目**: 待つ時間の間に消えた短い反応は、Note On にならない。指の検出とノートを切り離すこと自体が、ヒステリシスと同じような効き目を持つ。ただしこれで抑えられるのはノートの揺れで、指の追跡の揺れ（Released → Started）は §3.5 のとおりタッチの層で抑える
- **Note On の後は、しばらく音程を変えない**: Note On を出してから一定の時間は、position が動いてもノートを変えない（Move しない）。触れ始めの指の揺れでノートが動かないようにするため
- ~~**ごく短いタッチは鳴らさなくてよい（2026-11-13 決定）**: Note On を出す前（速さを測っている間）に指が離れたときは、Note On も Note Off も出さない。素早いスタッカートの打鍵がある程度短ければ音にならないが、それでよい~~ → 下の「Note On の出し方」で改めた（2026-11-13）。depth が `FLICK_DEPTH` を超えてから消えたもの（はじく）は鳴らし、超えずに消えたものだけを鳴らさない

**Note On の出し方（2026-11-13 決定）: 決め打ちの時間を待つのではなく、depth があるしきい値（`NOTE_ON_DEPTH`）に届くまで待ち、届くまでの時間を測る。** 通常の鍵盤楽器のベロシティとは考え方が違い、速い側は頭打ちにして、遅い側の違いをしっかり取る。

| 触れ方 | depth の動き | Note On を出す周期 | ベロシティ |
|---|---|---|---|
| 速く押す | すぐに `NOTE_ON_DEPTH` を超える | 超えた周期 | 最大。ある速さより速いものは同じとみなす |
| ゆっくり押す | 時間をかけて `NOTE_ON_DEPTH` を超える | 超えた周期 | かかった時間で下げる。ここを細かく取る |
| はじく | `NOTE_ON_DEPTH` に届かないまま、すぐ下がる。ただし最大の depth は `FLICK_DEPTH` を超えている | 下がり始めた周期 | 速いとみなす |
| かすっただけ | `FLICK_DEPTH` を超えないまま消える | 出さない | — |
| 軽く触れたまま | `NOTE_ON_DEPTH` に届かず、下がりもしない | 上限の時間が過ぎた周期 | 遅いとみなす |

- 時間は、指を検出した周期（depth が `TOUCH_ON_DEPTH` を超えた周期、§3.5）から数える。指を保持している周期（`Track::None`）も数える
- 速い側は頭打ちにするので、10ms 毎の分解能でよい（しきい値を超えた時刻の補間は要らない）。遅い側は何周期もかけて立ち上がるので、10ms 毎でも差が出る
- 「はじく」と「軽く触れたまま」は、どちらも depth が `NOTE_ON_DEPTH` に届かない場合で、depth が下がり始めたかどうかで分ける。下がり始めの判定は、ノイズで誤らないよう幅を持たせる（それまでの最大の depth から一定以上下がったら、など）
- 「はじく」の Note On は、`Released` を待たずに下がり始めた周期に出す。`Released` は指を失ってから 50〜60ms 後なので、待つと遅れる。Note Off は `Released` の周期に出す
- 「はじく」か「かすっただけ」かは、最大の depth が `FLICK_DEPTH` を超えたかどうかで決める（ユーザーの判断）。`FLICK_DEPTH` は `TOUCH_ON_DEPTH` と `NOTE_ON_DEPTH` の間の値になる
- **ベロシティで変えたいのは音量ではなく、音の立ち上がり（アタック）**（2026-11-13、ユーザー）

初めの値（2026-11-13 決定。数値の見当はつけずに、まず試す）:

- 下がり始め: depth が前の周期より下がった瞬間（幅は持たせない）。指を見失った周期（`Track::None` で触れている）も、下がったとみなす

`PlayInfo` の流れ（2026-11-13 方針。まずはシンプルなルールから始める）:

`PlayInfo` は、周期毎に `TouchPoint` 毎の `Track`・depth・position を受け、`Voice` 毎に状態を進める。タッチの層は今のまま（§3.4・§3.5 を入れても、`Track`・depth・position を出すことは変わらない）。

| 状態 | 入ってくる Track | すること |
|---|---|---|
| 待機 | `Started` | 測定中へ。depth の履歴を始める |
| 測定中 | `Followed` | depth を履歴に入れる。待つ時間が過ぎたら、速さからベロシティを決めて Note On → 発音中へ（2026-11-13 改め: depth が `NOTE_ON_DEPTH` に届いた・はじいた・上限の時間が過ぎた、のどれかで Note On。上の「Note On の出し方」） |
| 測定中 | `Released` | 何も出さずに待機へ（ごく短いタッチは鳴らさない。2026-11-13 改め: `FLICK_DEPTH` を超えずに消えたもの） |
| 発音中 | `Followed` | depth・position を履歴に入れる。音程を変えない時間が過ぎていれば、ノートが変わったときに Move |
| 発音中 | `Released` | Note Off → 待機へ |

- `Track` は今の役割のまま、同じ指が続いているかを示す。`Started` が来たら、その `Voice` は新しい指として初めからやり直す
- 指を保持している周期（`Track::None` で `is_touched()` が true）は、状態を変えず、depth を履歴に入れない。その周期の depth は、最後に見つけた周期の値のままで、その周期に測った値ではないため（§3.5）。今の位置の履歴と同じ扱い
- 「離す測定中」の状態は、初めは作らない。depth が下がっていくのは `Released` の前の `Followed` の間なので、発音中の depth の履歴から離すときの遅さを求められる。状態が要るかは、遅さの求め方を決めるときに判断する

手順（2026-11-13 方針）:

1. **状態を作るが、待つ時間は 0 にする**: 測定中をすぐ抜けるので、出るイベントは今と同じになるはず。記録（`.qlog`）を `replay_algo` に通し、前後で同じことを確かめる
    - 2026-11-13 実装（`crates/touch_algo/src/playinfo.rs`）: `Voice` に状態 `VoiceState`（`Idle`・`Onset`・`Sounding`）と、指を検出してからの周期数 `elapsed` を持たせた。`perform_notes` が `Track` と状態の組で動く。待つ周期数は `ONSET_WAIT_CYCLES`（0）で、`PlayInfo::set_onset_wait` で変えられる。`elapsed` は測定中の間、保持している周期（`Track::None` で触れている）も数える（待つのは時間なので）。Note On は `Followed` の周期（その周期に測った depth・position がある）に出す。depth の履歴はまだ持たない（手順 2 で足す）
    - テスト: `note_on_waits_for_onset`（待つ時間が過ぎた周期の position・depth で Note On）、`short_touch_within_onset_is_silent`（待つ間に離れたら何も出さない）。今までのテストはそのまま通る

## 5. 現状の実装（`QubitTouch`）の仕様

2026-11-13 に、§5.3 の 1〜2.5（山の探索・窓・統合）と `TOUCH_THRESHOLD`・`FINGER_RANGE`・`CANDIDATE_MERGE_RANGE` は、区間に置き換えた（§3.4・3.5 の実装）。以下は置き換える前の記録。

2026-11-08 時点の `src/touch/qtouch.rs`（同じ日に、処理を変えずに `crates/touch_algo/src/touch.rs` へ移した。§7.5）。Arduino 版から移植し、Rust 版で手を加えてきたもの（例: 単発のノイズを捨てる判定は 2026-07-05 のコミット 9c8dbfd で Rust 版に足した。Arduino 版には無い）。2026-10-03 以降は、`doc/touch_baseline.md` §4.6 で閾値などを 1/4 にした以外は変えていない。§3.4（1 本の指とみなす電極の範囲）は、これを元に決める。

### 5.1 呼び出し

`touch_task`（Core1）が、解析の周期（10ms 毎。`analysis_divider()`）に次を行う。

1. 全電極について `set_value(電極番号, touch_algo の output)`
2. `seek_and_update_touch_point(work_mode)`
3. `lighten_leds()`（今は何もしないコールバック）

Note On/Off と CC は、`QubitTouch::new()` に渡したコールバックで `MIDI_TX` に入れる。コールバックは `status` の上位 4 ビットにチャンネルを足すだけで、`note`・`velocity` はそのまま送る。

### 5.2 データ構造

| 構造 | 内容 |
|---|---|
| `Pad`（電極数ぶん） | 電極の output。移動平均の構造が残っているが、`MAX_MOVING_AVERAGE` = 1 なので値そのもの |
| 候補（`(f32, f32, i16)` × `MAX_TOUCH_POINTS`） | その周期で見つかった (山の電極番号, position, depth)。周期毎に作り直す |
| `TouchPoint`（`MAX_TOUCH_POINTS` = 4 個） | 周期をまたいで追跡するタッチ。position・depth（`intensity`）・今のノート・継続時間・位置の履歴（128 サンプル）を持つ |

### 5.3 処理の流れ（`seek_and_update_touch_point`）

1. **山を探す（`scan_pads`）**: 電極 0 から順に、隣との差の符号を見る。左隣より大きく、右隣より大きい（どちらも `>`）電極を山とし、その output が `TOUCH_THRESHOLD`（8）より大きければ候補にする。電極番号は `MAX_PADS` で巡回させる（最後の電極と最初の電極を隣とみなす）。候補が `MAX_TOUCH_POINTS`（4）個になったら、そこで探すのをやめる
    - 2026-11-08 変更: 平らな頂上も山にする（§6.1 の 1）。巡回させるのはリングの構成だけ（§6.1 の 4）
2. **depth と position を求める（`decide_touch_point`）**: 山を中心に、前後 `FINGER_RANGE`（3）電極、計 7 電極で
    - depth = 7 電極の output の合計（§3.2）
    - position = 7 電極の重心（§3.3）。電極番号は巡回させずに `山 − 3 〜 山 + 3` のまま掛ける
        - 2026-11-08 変更: 山からの相対位置（−3〜+3）で重心を取り、山の番号に足す。リングでは 0 以上電極数未満に巡回させる（§6.1 の 3）
    - ~~単発のノイズを捨てる: 山の電極が depth の 70% 以上（`SINGLE_PAD_SPIKE_RATIO_PERMILLE`）で、かつ周りの最大が山の 1/4 以下（`SINGLE_PAD_SPIKE_NEIGHBOR_DIV`）なら、候補を無効にする~~（2026-11-08 に外した。§6.1 の 10）
3. **近い候補をまとめる（`merge_close_candidates`）**: position の差が `CANDIDATE_MERGE_RANGE`（1.6 電極）以内の候補は、depth の大きい方 1 つだけを残す（position・depth は計算し直さない）
    - 2026-11-08 変更: まとめた候補の窓を合わせた範囲で計算し直す（§6.1 の 7）
4. **前の周期のタッチと結び付ける（`collate_touch_point`）**: 候補を順に、まだこの周期で更新していない TouchPoint のうち position の最も近いものと比べ、`CLOSE_RANGE`（3 電極）以内なら同じ指が動いたとして更新する。無ければ空いている TouchPoint で新しいタッチを始め、Note On を送る
    - 更新したとき、position がノートの境目を `HISTERESIS`（0.7 電極）越えたら、新しいノートの Note On と古いノートの Note Off（`RINGLED_CMD_TX_MOVED`）を送る
    - 2026-11-08 変更: リングでは、距離（`CLOSE_RANGE`・`HISTERESIS`・`CANDIDATE_MERGE_RANGE`）を近い向きに測る（§6.1 の 3）
5. **離れたタッチを消す（`erase_touch_point`）**: この周期に更新されなかった TouchPoint は、`RELEASE_WAITING_TIME`（5 周期 = 50ms）続けて更新が無ければ離れたとみなし、Note Off を送る。待っている間は position を保ち、候補が `CLOSE_RANGE` 以内に戻れば同じタッチとして続く
6. **継続時間とビブラート（`update_durations_and_vibrato`）**: どれかが触れていれば `on_time` を更新し `ANY_TOUCH` を立てる。Violin モードでは、position の履歴からビブラート（1.5〜8Hz の往復）を検出し、CC1・CC19 を送る

2026-11-08 に、この流れを depth・position の層と演奏情報の層に分けた（§5.6）。

### 5.4 ノートとベロシティ（§4 で扱う。参考）

- ノート: Piano は position を四捨五入した電極番号 + `PIANO_OFFSET`。Violin は position / 2 を四捨五入 + `VIOLIN_OFFSET`（2 電極で 1 ノート）
    - 2026-11-08 変更: リングでは、四捨五入で電極数（Violin は電極数 / 2）になったら 0 にする。リングでなければ 0〜電極数 − 1（Violin は 0〜電極数 / 2 − 1）に切り詰める。それまでの Violin は、12 電極で position が 11 付近のとき 6 になり、ノートの範囲（0〜5）を外れて更新されなかった
- ベロシティ: Piano は Note On の周期の depth から `100 + depth / 4`（100〜115）、depth > 63 で 127（Arduino 版の 255 を 2026-11-08 に 127 にした。§6.3 の 1）。Violin は直前のノート・継続時間・離していた時間から決め、depth は使わない

### 5.5 定数

| 定数 | 値 | 意味 |
|---|---|---|
| `TOUCH_THRESHOLD` | 8 | 山の output がこれより大きければ候補にする |
| `FINGER_RANGE` | 3 | depth・position を求める片側の電極数（計 7 電極） |
| `SINGLE_PAD_SPIKE_RATIO_PERMILLE` | 70 | 山の電極が depth のこの % 以上なら単発のノイズの候補（名前は ‰ だが % として使っている）。2026-11-08 に削除（§6.1 の 10） |
| `SINGLE_PAD_SPIKE_NEIGHBOR_DIV` | 4 | 周りの最大が山の 1/4 以下なら単発のノイズの候補。2026-11-08 に削除（§6.1 の 10） |
| `CANDIDATE_MERGE_RANGE` | 1.6 | 同じ周期の候補をまとめる距離（電極） |
| `CLOSE_RANGE` | 3.0 | 前の周期のタッチと同じ指とみなす距離（電極 / 10ms） |
| `HISTERESIS` | 0.7 | ノートを切り替える position のヒステリシス（電極） |
| `RELEASE_WAITING_TIME` | 5 | 離れたとみなすまでの周期数（50ms） |
| `MAX_TOUCH_POINTS` | 4 | 候補・TouchPoint の最大数（`constants.rs`） |


### 5.6 層の分け方（2026-11-08）

§3.6 の方針で、`QubitTouch` を 2 つの層に分け、別のファイルにした。depth・position の層は、ノートを知らない。演奏情報の層は、電極の output を見ない。呼び出し側は、毎周期 `TouchTracker::update()` → `PlayInfo::update(&tracker, 動作モード)` の順に呼ぶ。

| 層 | ファイル・型 | 処理 | 持つもの |
|---|---|---|---|
| depth・position（§3） | `touch.rs` の `TouchTracker` | 1. 山を探す（`scan_pads`）→ 2. depth・position（`decide_touch_point`）→ 2.5. 候補をまとめる（`merge_close_candidates`）→ 3. 前の周期の指と結び付ける（`track_touch_points`）→ 4. 離れたかの判断（`release_touch_points`） | 電極の output、`TouchPoint`（指毎）: position・depth・継続時間と、この周期の追跡の結果 `Track`（`Started`・`Followed`・`Released`・`None`） |
| 演奏情報（§4） | `playinfo.rs` の `PlayInfo` | 5. `Track` から Note On/Off（`perform_notes`: `note_start`・`note_follow`（→ `move_note` / `cross_seam`）・`note_release`）→ 6. 継続時間とビブラート（`update_durations_and_vibrato`） | コールバック、`Voice`（指毎）: 鳴らしているノート・offset・ノートの数・ノートの決め方（Piano / Violin）・位置の履歴（ビブラート用）。直前のノート・継続時間・離していた時間（Violin のベロシティ用） |

- 定数も層で分けた。`touch.rs`: `MAX_TOUCH_POINTS`・`TOUCH_THRESHOLD`・`CLOSE_RANGE`・`FINGER_RANGE`・`RELEASE_WAITING_TIME`・`CANDIDATE_MERGE_RANGE`（`SINGLE_PAD_SPIKE_*` は後で削除。§6.1 の 10）。`playinfo.rs`: `HISTERESIS`・`PIANO_OFFSET`・`VIOLIN_OFFSET`・`STATUS_*`・`WorkMode`・ビブラートの定数
- `PlayInfo` が `TouchTracker` から読むのは、指毎の `track()`・`get_location()`・`last_location()`・`get_intensity()`・`touching_time()` と、電極の並び（電極数・リングか）だけ
- 位置の履歴は演奏情報の層に移した（ビブラートを見るためのもので、depth・position には要らない）。新しいタッチ（`Started`）で今の position で埋め、`Followed` で足す
- 5 は、始まり・動き（`Started`・`Followed`）を先に、離れた（`Released`）を後に処理する。今までの順番（結び付けで Note On・Move、その後に Note Off）と同じ
- 離れた後も `TouchPoint` は最後の position を残す（`last_location()`。Note Off のコールバックの location に使う）。`get_location()` は、触れていなければ今までどおり 100.0 を返す
- 分ける前と後で、記録 `qubit_20261027_211117.qlog`（12 電極）を PC で通した結果（イベントの時刻・ノート・ベロシティ・location）は同じだった。違うのは、同じ周期に複数の指が始まった・動いたときのイベントの順番（今までは候補の順、今は TouchPoint の順）と、ノートの決め方がエラーを返したとき（今までは TouchPoint を使わなかった。今は追跡は続け、ノートを鳴らさない。Violin で電極が 1 つのときだけ起きる）

### 6.1 1 本の指の範囲・depth・position（第一の目標。§3.4 で扱う）

1. ~~**平らな山を見落とす（確実）**~~: 山の判定が両側とも `>` なので、隣り合う 2 電極が同じ値の山（例: output が 3, 10, 10, 2）は候補にならない。指がちょうど 2 電極の間にあるときに起きやすい。その周期はタッチが無いことになり、50ms 以内に戻れば `RELEASE_WAITING_TIME` で隠れるが、depth・position が更新されず、続けば Note Off になる

    - ~~4〜6 電極離れた 2 本の指は、窓が重なり、互いの output を取り込む。depth が大きくなり、position が互いに寄る（第三の目標で効く）~~ → §3.7 で、決め打ちの距離（初めは 6 電極）以内の指は分けないことにしたので扱わない（2026-11-08）
3. ~~**リングのつなぎ目で position が巡回しない（確実）**~~: 窓の電極の値は巡回させて読むが、重心には電極番号を巡回させずに掛ける。山が電極 0 の近くなら position は負になりうる（例: −0.4）、最後の電極の近くなら `MAX_PADS − 1` を超えうる。さらに
    - ノートの計算で 0〜`MAX_PADS − 1` に切り詰めるので、つなぎ目の近くでは position の変化がノートに出ない
    - 指がつなぎ目を越えると、position が約 `MAX_PADS` 飛ぶので、`CLOSE_RANGE` に入らず、別のタッチになる（Note Off と Note On が出る）
    - 2026-11-08 修正: 重心の計算を 2 通りにし、6.1 の 4 の `ring` で切り替える。読み方と重心の計算は組で決まるので、別々には選べないようにした（巡回させて読むのに重心は巡回させない、が今までのバグ）
        - リング（true）: 山からの相対位置で重心を取り、0 以上電極数未満に巡回させる（`window_centroid`）
        - リングでない（false）: 範囲外の電極は output 0 として読むので、重心に効かない。position は 0〜電極数 − 1 に収まる

### 6.2 タッチの有無・追跡（§3.5 で扱う）

1. **触れ始めの判定が山の値だけ**: 山の電極の output が 8 を超えた最初の周期で、すぐに Note On を出す。depth は見ない。ヒステリシスも無いので、しきい値の近くでは、6.1 の 1 などで途切れたときに、離れたかどうかが `RELEASE_WAITING_TIME` 頼みになる
    - 2026-11-12 方針: 指の有無は depth で決め（§3.5）、Note On は指の検出から遅らせて出す（§4.2）
2. **離れてから 50ms は同じタッチ**: 離れても 50ms は TouchPoint が残るので、その間に 3 電極以内を叩き直すと、新しいタッチにならない
    - 同じ電極を叩き直すと、Note On が出ない（連打が抜ける）
    - 近くの電極を叩くと、移動として扱われ、Note Off・Note On（MOVED）になる
3. **結び付けが候補の順番による**: 候補を電極番号の順に、その時点で最も近い TouchPoint に結び付ける（貪欲法）。2 本の指が近づいたとき、入れ替わることがある（第三の目標で効く）。§3.7 で決め打ちの距離以内の指は分けないことにしたので、入れ替わりが起きうるのはそれより離れた指どうしだけ（2026-11-08）
4. **TouchPoint が空いていないとき**: 4 個とも使っている（離れるのを待っているものを含む）と、新しい候補は何も言わずに捨てられる

### 6.3 演奏情報（§4 で扱う）

1. ~~**Piano のベロシティが MIDI の範囲を超える（確実）**~~: `default_note_on_velocity()` は 100〜115 か 255 を返し、コールバックはそれをそのまま Note On のデータバイトにしていた。MIDI のデータバイトは 0〜127 なので、128 以上は不正な値になる。Arduino 版から引き継いだもの

2. **ベロシティを触れ始めの 1 周期で決める**: Note On は depth が 8 を超えた最初の周期で出るので、depth はほとんど立ち上がっていない。ベロシティは触れ方によらず、ほぼ一定（100〜110）になる
    - 2026-11-12 方針: Note On を遅らせ、depth の立ち上がりから触れる速さを求めてベロシティにする（§4.2）
3. ~~**位置の履歴を新しいタッチで消さない（確実）**~~: `location_history` は TouchPoint を使い回しても初期化しない。新しいタッチから 1.28 秒（128 サンプル）は、前のタッチの position と混ざり、ビブラートを誤って検出することがある（Violin モード）

5. ~~**つなぎ目の上のビブラート（確実。リングだけ）**~~: 位置の履歴は巡回した position（0 以上電極数未満）のまま入れるので、つなぎ目の上で指を揺らすと、履歴が 0 付近と電極数付近を行き来する。最小・最大・平均が大きく外れ、検出がおかしくなる。履歴に入れるときに、前の値から近い向きにつなげた値（巡回させない値）にすれば直る（2026-11-08、6.1 の 3 の修正で見つけた）。§4.1 のルールで、position が 95 以上の間は検出した値を出さないことにした
    - 2026-11-08 修正: §4.1 のとおり（`update_durations_and_vibrato`）。位置の履歴は巡回した position のまま

### 7.1 クレートとファイル

新しいクレートは作らず、`crates/touch_algo` に入れて、ファイルを分ける。

（2026-11-08 追記）下の表の後、`touch.rs` をさらに depth・position の層（`touch.rs`）と演奏情報の層（`playinfo.rs`）に分けた（§5.6）。

| ファイル | 内容 | 扱う単位 |
|---|---|---|
| `src/lib.rs` | モジュールの宣言だけ | |
| `src/electrode.rs` | 今の `lib.rs` の中身（ノイズ除去・基準値・noise_floor。`doc/touch_baseline.md`） | 電極 1 つずつ |
| `src/touch.rs` | `src/touch/qtouch.rs` から移すもの（本書） | 指 1 本 = タッチ |

1 つのクレートにする理由:
- 使うところが同じ（ファームの `touch_task` と qubit_etude）で、必ず「信号処理 → 解析」の順につないで使う。片方だけ使う場面が無い
- どちらも no_std・依存無し・ホストでテストする。クレートを分けると `Cargo.toml`・path 依存・テストの手順が 2 つずつになる
- noise_floor の大きい電極の扱い（§6.1 の 5）のように、信号処理の出し方と解析の受け取り方を一緒に変えることが多い

### 7.2 名前の付け方（2026-11-08 決定）

電極 1 つの処理も、指 1 本の処理も「touch」と呼んでいて紛らわしいので、次のように分ける。

- 電極 1 つの単位のもの: **electrode**
- 指 1 本の単位のもの: **touch**（§2）

これに沿って、名前を次のように変えた（2026-11-08 実装）。

| 今の名前 | 新しい名前 | 備考 |
|---|---|---|
| `touch_algo::TouchSignal` | `touch_algo::electrode::ElectrodeSignal` | 電極の信号処理なのに Touch と付いている |
| `touch_algo::KeyState` | `touch_algo::electrode::ElectrodeState` | |
| `touch_algo::Params` / `State` / `MAX_SMOOTH_SAMPLES` | `touch_algo::electrode::` の下に移す（名前はそのまま） | 解析のパラメータは `touch_algo::touch::` に別に置く |
| `QubitTouch`・`TouchPoint` | `touch_algo::touch::` に移す（名前はそのまま） | |
| `Pad` | 無くす | 電極の output をそのまま配列で受け取れば足りる（§6.4） |

- ファームの定数（`TOTAL_QT_KEYS` など）と、`src/touch/`（`read_touch.rs` など）の名前は今回は変えない。AT42QT1070 の用語（key）に合わせたもので、変えると範囲が広がるため（§9）

### 7.3 移すときに外すファームへの依存

`qtouch.rs` はほとんどが計算で、ファームに頼っているのは次の 4 つだけ。

1. **共有状態への書き込み**: `TOUCH0-3`・`ANY_TOUCH`・`DEBUG_VALUE` を中で書いている。外して、タッチの状態（position・depth・触れているか）を読み出せるようにし、Atomic へ書くのは `touch_task` で行う
2. **電極数**: `TOTAL_QT_KEYS`（feature で 6 / 12 / 96 に変わる）を定数で使っている。PC では記録によって変わるので、`TouchSignal<K>` と同じく外から与える。リングかどうか（§6.1 の 4）も一緒に渡す
3. **定数と型**: `MAX_TOUCH_POINTS`・`PIANO_OFFSET`・`VIOLIN_OFFSET`・`WorkMode`・`RINGLED_CMD_*`・`MIDI_CC`。`touch_algo` に移し、ファームの `constants.rs` はそれを使う
4. **MIDI の出力**: 今のコールバック `Fn(status, note, velocity, location)` はそのまま使える。PC ではイベントを溜めて表示する

### 7.4 手順

1. **動作を変えずに移す**: §6 のバグもこの段階では直さない
2. **同じに動くことを確かめる**: 記録（`.qlog`）にはファームが出した Note On/Off/Moved の EVENT も入っている。記録を PC で `electrode` → `touch` に通し、出てきたイベントが記録のイベントと一致するかを比べる
    - ファームは解析を 10ms 毎に呼ぶ（`analysis_divider()`）。PC でも記録したときのスキャン周期から同じフレームを選んで渡さないと一致しない
3. **qubit_etude に表示を足す**: タッチの position・depth と Note のイベント。まず `replay_algo` の出力に足し、GUI はその後
4. **PC でバグを直す**: §6 のバグを直し、記録で直す前と後を比べてから、ファームに入れる

### 7.5 手順 1 の実装（2026-11-08）

処理は変えずに移した。§6 のバグもそのまま残っている（ベロシティ（§6.3 の 1）だけは、実機で試す前に直した）。移すときに変えたのは次の点。

- **電極数**: `QubitTouch<F, P>` の `P`（`[u16; N]` や `Vec<u16>`）で渡す。`QubitTouch::new(コールバック, 0 で埋めた P)`。電極数を使っていた計算（`new_location_piano` / `_violin` の切り詰め、`collate_touch_point` の初期値）には、`P` の長さを渡す。電極数が 0 のときは何もしない（PC 向け）
- **`Pad` を無くした**: `MAX_MOVING_AVERAGE` = 1 では値そのものなので、`P` の値を直接使う
- **共有状態**: `TOUCH0-3`・`ANY_TOUCH`・`DEBUG_VALUE` は `touch_task` の `publish_touch_state()` が解析の後に書く。読み出しに `touch_point(id)`（`is_touched()`・`get_location()`・`get_intensity()`）・`is_any_touched()`・`vibrato()` を足した
    - `TOUCH0-3` は、これまで変化のあったタッチポイントだけを解析の途中で書いていた。今は毎回 4 つとも書く。書く値（触れていれば position ×100、触れていなければ 10000）は同じ
- **定数と型**: `MAX_TOUCH_POINTS`・`WorkMode`・`KEYBD_LO`・`PIANO_OFFSET`・`VIOLIN_OFFSET` を `touch_algo::touch` に移した。ファームの `constants.rs` は `MAX_TOUCH_POINTS` と `WorkMode` を再公開する
- **コールバックの status**: `STATUS_NOTE_ON`（0x90）・`STATUS_NOTE_OFF`（0x80）・`STATUS_NOTE_MOVED`（0xa0）・`STATUS_CC`（0xb0）を `touch_algo::touch` に置いた。ファームの `RINGLED_CMD_TX_*`・`MIDI_NOTE_ON`・`MIDI_NOTE_OFF`・`MIDI_CC` は使うところが無くなったので消した
- **公開の範囲**: 使われていなかった `_deb_val`・`_debug`・`get_touch_point`（`&mut`）・`proper_pad` を消し、`_get_value` → `value`、`_get_touch_count` → `touch_count`、`_touch_point` → `touch_point` にした
- **テスト**: ホストのテストを 2 つ足した（1 本の指の Note On/Off、指を動かしたときの Note On と MOVED）

### 7.6 qubit_etude での表示（2026-11-08、手順 3）

- `algo.rs`（`AlgoRunner`）: 信号処理の後、同じフレームで output を `QubitTouch`（今は `TouchTracker` → `PlayInfo`）に渡して解析する（動作モードは Piano）。タッチポイント毎の (position, depth) と、出てきたイベントを時刻と一緒にためる。ファームは信号処理と解析を 10ms 毎に行うので、同じ条件にするには間引きを 10ms にする
- GUI: 右の欄の「タッチ」タブ（2026-11-08 に右の欄を「電極」「統計」「タッチ」のタブに分けた。イベントが出るたびに欄の高さが変わり見づらかったため）。OLED の Touch ページと同じく Touch1〜4 の position（触れていなければ ---）を、depth と一緒に出す。表示範囲の最後の値（一時停止中は範囲の終わり）。その下に、PC の解析が出したイベント（表示範囲、新しい順に 10 件。行数は固定で、件数が少なくても高さは変わらない）
- GUI（2026-11-08 追加）: 下のバー表示（output）のすぐ下に、タッチのグラフ（`touch_plot`）。横軸はバー表示と同じキーの範囲で、位置もそろえる（左の［+］［−］と同じ幅をあけ、縦軸の幅 `BAR_Y_AXIS_WIDTH` を両方で同じにする）。表示範囲の最後の値（一時停止中は範囲の終わり）
    - 触れている指毎に、position の位置に円を描く。面積は depth に比例する（半径 ∝ √depth。depth が `TOUCH_FULL_DEPTH`（200）で半径がグラフの高さの 0.45 倍）。小さすぎて見えなくならないよう、半径は 3px 以上
    - 円は周縁ほど薄い（同じ中心の円を 16 枚、不透明度 0.15 で外から順に重ねる）。色は指の番号毎で、中心に番号（1〜4）
- `replay_algo`: PC の解析のイベントと、記録の中のファームのイベントを並べて出す
