# I2Cロックアップ問題 - 切り分けまとめ

## 症状
- Seeed XIAO RP2350 の I2C バスに、SSD1306 OLED と PCA9544(4個) が接続
- 各 PCA9544 の下に AT42QT1070 が4個ずつ接続
- 4つの PCA9544 のうち **3つ目(dev==2, アドレス0x72)** にアクセスすると、バス全体がロックアップ(SDA/SCL 両方とも約1.0Vで膠着)し、OLEDも表示されなくなる
- SDA単独・SCL単独の接続では問題は起きない。両方接続し、かつファームウェアがそのPCA9544に**アクセスした瞬間のみ**発生する

## 経緯(時系列)
1. 以前から特定のAT42QT1070(「ダメなAT」)が時々動かないことがあった(原因不明)
2. 修理のため取り外し・半田点検・再接続 → I2C全体が動かなくなった
3. 問題の PCA9544(#3, dev==2)を外すと、他は正常動作することを確認

## 現時点で「除外できた」原因
- PCA9544チップ個体の不良(新品交換済み)
- #3ブランチの基板そのものの不良(新品作成済み)
- GND/VCCの接続不良
- SDA-SCL間の物理的な短絡
- AT42QT1070側の不良(ATを外しても再現)
- I2Cバス容量過多(クロック速度を落としても再現)
- ソフトウェアのタイムアウト設定
- アドレス設定・アドレス衝突
- /INTピンのフローティング
- PCA9600Dバッファとの非互換性(バッファ除去後も再現)

## 現時点で「まだ結論が出ていない」こと
- **PCA9544基板そのもの(チップ・基板とも新品)なのに、なぜ#3の位置でだけ再現するのか**という根本的な謎は未解決
- 子バス(AT側)がロックアップを誘発し、それが親バス(マイコン-PCA9544間)に伝播した可能性は理論上否定できないが、`pca.select()`(チャンネル未選択の時点)で既にタイムアウトしているため、現状は親バス側の問題である可能性が高いと考えている

## 次回、配線を外しながら一つずつ繋ぐ際に確認したいポイント
1. #2→#3、#3→#4間の接続を1本ずつ(SDA、SCLそれぞれ単独)確実に極性を確認しながら再接続する
2. 「入れ替えると症状が変わる」という事実があるため、単純な配線ミスの可能性は依然として排除しきれない。テスタでの導通確認だけでなく、**実際にマイコンから信号を出した状態でのオシロ波形**を、可能であれば個別に確認する
3. 「#3チップ単体を、正常に動く#4の位置(配線)に繋いだ場合」「#4チップ単体を#3の位置(配線)に繋いだ場合」の入れ替えテストはまだ未実施。可能であれば試す
4. ロジックアナライザまたは複数chオシロでの波形キャプチャができれば、START条件・ACK/NAKの有無が確認でき、決定的な手がかりになる

## 応急対応の選択肢(根本解決を保留する場合)
1. コード上、`dev == 2`(#3)へのアクセスをスキップする(既にコメントアウトで実装済み)
2. タイムアウト検出時にSCLの手動クロックパルス+I2Cペリフェラル再初期化による「バスリカバリー」処理を追加する
3. #3を含むブランチを別のI2Cバス(RP2350のI2C0など)に分離し、ロックアップの影響がOLEDや他のPCA9544に及ばないようにする
