# タッチセンサ信号処理（基準値の自前管理・ノイズ対策） 設計書

2026-11-14 に、対応済みの項目・置き換える前の実装の記録を削除して整理した（古い内容は git の履歴にある）。

## 1. 背景と目的

### 1.1 現状

- `read_touch`（`src/touch/read_touch.rs`）は AT42QT1070 から生値（Key Signal、レジスタ 4–15）だけを読み、生値と読み取り成功フラグ（`valid`）を返す。チップの基準値（Reference Data）は使わない
- `touch_task`（Core1）が `crates/touch_algo` の `ElectrodeSignal` で電極毎の output を作り、解析（`TouchTracker`、`doc/touch_analysis.md`）に渡す
- スキャンは `touch_task` の `Ticker` で一定周期（既定 10ms、`constants.rs` の `SCAN_PERIOD_US`）、信号処理と解析は 10ms 毎。`debug_stream` feature では周期の既定が 2ms で、PC から 2 / 5 / 10 / 20ms に変えられる（`doc/debug_env.md`）

### 1.2 チップの基準値を使わない理由

データシート（`doc/Atmel-9596-AT42-QTouch-BSW-AT42QT1070_Datasheet.pdf`）を見ると、チップの基準値は「ボタンの ON/OFF 判定」を目的に作られており、QUBIT のように差分の大きさを連続量として使う用途には合わない。

| 項目 | データシートの記述 | QUBIT への影響 |
|---|---|---|
| ドリフト速度（§2.11.1） | タッチ方向へ 1 カウント / 2.88 秒、反対方向へ 1 カウント / 0.96 秒 | 数十カウントのずれを吸収するのに数十秒〜数分かかる |
| Drift Hold Time（§2.11.6） | 1 キーでも検出中なら、同じチップの全キーでドリフトが止まる。離してから約 4 秒は止まったまま | 演奏中は 6 キーのどれかが触れられていることが多く、基準値がほぼ固定になる |
| 検出しきい値 NTHR | 既定 20 カウント。検出中のキーはドリフトしない | こちらの判定とずれるため、いつ止まり、いつ動くのかを外から予測できない |
| Max On Duration（§2.11.4） | `init()` で 0（無効）にしている | 検出状態のまま固まったキーが二度と再校正されない |
| Positive Recalibration（§2.11.5） | 生値が基準値より 4 カウント以上下がると即座に再校正 | 下方向の追従は速いので、この挙動は自前実装でも踏襲する |

また、生値にはかなりのノイズが乗っている。ノイズ除去は信号処理の層（§3.3）で行う。

### 1.3 AT42QT1070 の測定タイミング（データシートより）

- 約 8ms の固定サイクルで動作する（§2.5）。`init()` は LP_MODE = 0 に設定しているので、毎サイクル（8ms 毎）に測定する
- Averaging Factor（AVE、レジスタ 39–45。既定 8）を大きくすると S/N は良くなるが、測定時間が延びる。全キーの測定が 8ms を超えると、ステータス（レジスタ 2）の OVERFLOW ビットが立ち、サイクルが延びる（§2.5, §5.4）
- 16 個のチップはそれぞれ自走しており、互いに同期していない。各キーの生値はおよそ 8ms 毎に更新される
- 同期していないため、チップの境目の隣り合うキーに、隣のチップの測定によるノイズが入る（§3.12）

したがって、**生値の時間分解能は 8ms が上限**になる。

- 使っていない key6 は `init()` で無効にしている（AVE/AKS のレジスタ 45 に 0 を書く。データシート §2.3）。無効にする前は更新間隔が 10ms 前後に見えた（2026-10-03）
- 96 キーでは 1 周に 8ms 前後かかり、チップの更新が 8ms でも 10ms でも得られる分解能はほとんど変わらないため、正確な更新周期にはこだわらない

### 1.4 方針

1. チップからは **生値（Key Signal）だけ** を読み、基準値はファームウェアでキーごとに管理する
2. ノイズ除去は信号処理（`touch_algo::electrode`）で行う
3. スキャン → 信号処理 → 解析が Core1 の `touch_task` の中でひと続きに行われる（`doc/task_architecture.md`）
4. **速さ（ベロシティ）の検出は信号処理では扱わない**（2026-10-03 決定）。生値は自由に上下するので、キー 1 つの delta から立ち上がりの始まりを決めるのは難しい。複数の電極からタッチを求める解析の層で、depth の立ち上がりから測る（`doc/touch_analysis.md` §4.2）。信号処理は output を作るところまでとする
5. **ゆっくり触れても、基準値に吸収されずに反応すること** を優先する。ノイズ除去による遅れと鈍りは、速く触れたときの立ち上がりを鈍らせるが、それは許容する
6. 基準値の追従規則・速度・停止条件、フィルタの強さはすべてパラメータ（`Params`）で調整できるようにする
7. 基準値とノイズ幅（デッドゾーン）を別の量として管理し、二重に引かれないようにする

## 2. 用語

| 用語 | 意味 |
|---|---|
| raw | AT42QT1070 の Key Signal。指が近づくと値が増える |
| filtered | raw にノイズ除去（§3.3）をかけた値 |
| baseline | 未タッチ時の filtered の推定値。本設計で自前管理する |
| delta | `filtered - baseline`（符号付き）。正がタッチ方向 |
| noise_floor | 未タッチ時の delta の揺れ幅。出力から差し引くデッドゾーン |
| output | `max(0, delta - noise_floor)`。解析（`TouchTracker`）に渡す値 |
| 近傍 | リング上で自キーから ±`NEIGHBOR_RANGE` 以内のキー（`TOTAL_QT_KEYS` で折り返す） |

キー番号は読み取り順のインデックスのままで、そのままリング上の並びになる（2026-10-24 に回転をやめた。`debug_env.md` §1.2）。

時間に関する定数は、すべて **ミリ秒で定義** する。スキャン周期を変えても意味が変わらないようにするため。

## 3. 仕様

### 3.1 信号処理の流れ

```
[Core1: touch_task]
  AT42QT1070 (8ms 周期で自走)
    │ I2C 読み取り（scan_period_us() 毎）
    ▼
  raw（hi/lo ずれは読み直し済み）──► スパイク除去（3 点メディアン）──► 平滑化（短い移動平均）──► filtered
                                                                                              │
                                   baseline（§3.4–3.7、BASELINE_UPDATE_INTERVAL_MS 毎に更新）◄┤
                                                                                              ▼
                                                        delta = filtered - baseline ──► output
    │ 関数呼び出しで渡す（同じタスクの中。コアはまたがない）
    ▼
  TouchTracker → PlayInfo（doc/touch_analysis.md）: depth・position・追跡・ノート・ベロシティ
    │ ノートイベント
    ▼
  MIDI_TX ──► Core0: midi_tx_task
```

### 3.2 スキャン周期

- Core1 のスキャンループを `Ticker` で **`scan_period_us()` 毎**（既定値は `constants.rs` の `SCAN_PERIOD_US`）に回す。サンプル間隔が一定になり、フィルタの係数が時間として意味を持つ
- スキャン周期はチップのサイクル（8ms）以上にする（`debug_stream` で 2ms にするのは、チップの更新を観察するため）
- 1 周のスキャン時間は、見積もりでは 1 チャンネルあたり約 0.5ms × 16 チャンネル ≒ 8ms 前後。96 キーで **実測** し、スキャン周期を決める（8ms か 10ms の想定。今の既定は 10ms）
- 周期に間に合わなかった場合でも、フレームの時刻は実際にスキャンした時刻を記録する

### 3.3 ノイズ除去

キーごとに、次の順で処理する。

1. **hi/lo ずれ補正**: ファームの `read_touch` で、前回値との差が 220（`HI_LO_REREAD_DIFF`）以上のキーだけ、その場で読み直す（2026-10-02 決定・実装）
    - 原因: AT42QT1070 は 16bit の値の 2 バイトをまとめて固定しない（データシート 4.3.2 の Note）。上位を読んでから下位を読むまでの間にチップが値を更新し、値が 256 の境目をまたぐと、約 ±256 ずれた値が読める。ずれるのはその 1 回の読み込みだけ
    - 次の更新は 8ms 後なので、すぐ読み直せば正しい値が得られる。本当に大きく変化したときは同じ値が読めるだけで、値を誤らない
    - 読み直しはずれたキー 1 つだけ（`At42Qt1070::read_1key`）。失敗したら前回の値を使う
    - 以前に記録した `.qlog`（読み直しを入れる前）を再生すると、ずれはスパイクのまま見える（3 点メディアンで filtered からは取り除かれる）
2. **スパイク除去**: 直近 3 サンプルのメディアン。単発のスパイクを取り除く。遅れは 1 サンプル
3. **平滑化**: 直近 `SMOOTH_SAMPLES` サンプルの移動平均。遅れは (N−1)/2 サンプル

速さへの影響（スキャン周期 8ms の場合）:

| 構成 | 合計の遅れ | 立ち上がりの鈍り |
|---|---|---|
| メディアン 3 + 平均 2 | 約 12ms | 小 |
| メディアン 3 + 平均 4 | 約 20ms | 中 |

- 遅い方向（数十〜数百 ms かけた立ち上がり）の計測には、どちらの構成でもほとんど影響しない
- 速い方向（1〜2 サンプルで立ち上がる）は平滑化で鈍る。解析の層で速さを測るときの制約になる（方針 4・5）
- 読み取りに失敗したサンプルは、フィルタの履歴に入れない（前回の filtered をそのまま使う）
- メディアンは 3 サンプルそろうまで最新の値を使う。移動平均もそろうまではある分で平均する

### 3.4 基準値のデータ構造（キーごと、`ElectrodeState`）

| フィールド | 型 | 内容 |
|---|---|---|
| `baseline_q` | `u32` | 基準値の固定小数点表現（Q8、`filtered << 8` 相当）。遅い追従が丸め誤差で消えないようにする |
| `noise_floor` | `u16` | デッドゾーン |
| `quiet_since` | `Option<u32>` | 近傍が静かになった時刻（µs） |
| `neg_since` | `Option<u32>` | delta が大きく負になり始めた時刻（即時再校正用） |
| `stuck_since` | `Option<u32>` | delta が `QUIET_THRESHOLD` 以上（静かでない）になり始めた時刻（固着検出用。§3.7） |
| `stuck_min` / `stuck_max` | `u16` | 固着検出区間の filtered の最小・最大 |
| `recovering` | `bool` | 固着からの回復中か |

ほかに初期取得の積算（`acquire_sum` / `acquire_count`）や、noise_floor を計り始めたか（`noise_measured`）を持つ。時刻は u32 の µs で、差は `wrapping_sub` で求める。フィルタの履歴を合わせても、96 キーで数 KB に収まる。`ElectrodeSignal` は `touch_task`（静的に確保される future）の中に置くため、スタックへの影響は小さい。

全体の状態として、次を持つ。

- `state`: `Acquiring`（初期取得中）/ `AutoCalibrating`（起動時の noise_floor の自動計測中。§3.12）/ `Running`（通常）/ `Calibrating`（設定画面中）
- `last_update`: 基準値を最後に更新した時刻
- `prev_calibrating`: 設定画面に入った瞬間を検出するための、`process()` の `calibrating` の前回値

### 3.5 初期取得（Acquiring）

1. `ACQUIRE_MS` の間、キーごとに filtered を積算する
2. 平均値を `baseline_q` の初期値にする
3. 取得中の output は全キー 0 とする（解析にタッチとして見えないようにする）
4. 読み取りに失敗したサンプルは積算から除外し、成功回数で割る。1 回も成功しなかったキーは、次に読めたときの filtered をそのまま初期値にする

起動時に触れていた場合、そのキーの baseline は高めに取得される。指を離すと delta が大きく負になるので、§3.6 の R2 で自動的に回復する。

### 3.6 基準値の追従規則（Running）

`BASELINE_UPDATE_INTERVAL_MS` 毎に、キーごとに上から順に判定して、最初に当てはまった規則を適用する。

| # | 条件 | 動作 | 意図 |
|---|---|---|---|
| R1 | 読み取り失敗中（前回値を流用している） | 更新しない | 古い値で基準値を動かさない |
| R2 | `delta < -NEG_RECAL_THRESHOLD` が `NEG_RECAL_MS` 以上続いた | `baseline = filtered`（即時再校正） | チップの Positive Recalibration 相当。起動時タッチ・急な環境変化からの復帰 |
| R3 | `delta < -noise_floor`（`fall_deadband`、§3.12） | `baseline += (filtered - baseline) >> FALL_SHIFT` | 下方向は速めに追従。不感帯でノイズの谷に張り付かないようにする |
| R4 | 近傍が静かで、その状態が `QUIET_HOLD_MS` 以上続いている | `baseline += (filtered - baseline) >> RISE_SHIFT`。ただし 1 回の上昇は `RISE_MAX_STEP_Q` まで | 上方向（タッチ方向）はゆっくり追従。上限を付けて、手をかざしたままでも吸収速度を抑える |
| R5 | それ以外（近傍が触れられている） | 更新しない | 演奏中のタッチを基準値に取り込まない |

**「近傍が静か」の定義**

- 自キーと近傍の全キーで `delta < QUIET_THRESHOLD + noise_floor`（`quiet_adapt`、§3.12。ノイズの多いキーが、自分と近傍の上方向の追従を止めないようにする）
- 近傍を含めるのは、指の周辺のキーも近接で raw が上がるため。自キーだけで判定すると、指の周辺キーの基準値が少しずつ上がってしまう
- 近傍が一度でも静かでなくなったら `quiet_since` をリセットする（チップの Drift Hold Time の考え方を、チップ単位ではなく近傍単位にしたもの）
- 6 キーでは近傍の片側は `min(NEIGHBOR_RANGE, キー数/2)` にする（リングの折り返しで同じキーを 2 度数えないため）

**ゆっくりしたタッチを吸収しないための制約**

ゆっくり近づく指は、基準値から見ると「ゆっくり上がるドリフト」と見分けがつかない。ゆっくり触れても反応するよう、次を満たすようにパラメータを決める。

- 想定する最も遅いタッチ（`SLOWEST_ATTACK_MS` かけて、発音に必要な delta まで上がる。ここでは仮に 24 とする）の間に、基準値が上がる量が `QUIET_THRESHOLD / 2` 以下であること
- R4 で上がり得る量の上限は「`QUIET_THRESHOLD` を下回っている時間 × 上昇速度の上限」。上昇速度の上限は `RISE_MAX_STEP_Q / 256` カウント ÷ `BASELINE_UPDATE_INTERVAL_MS` で決まる
- 例: `SLOWEST_ATTACK_MS` = 1000ms、`QUIET_THRESHOLD` = 8 なら、`QUIET_THRESHOLD` 未満の区間はおよそ 1000 × 8/24 ≒ 330ms。上昇速度の上限を 3 カウント/秒とすると、吸収されるのは約 1 カウントで、条件（4 以下）を満たす
- さらに `QUIET_HOLD_MS` の待ちがあるため、直前まで演奏していた場所ではこの吸収は起きない

### 3.7 固着からの回復・ノイズ幅・設定画面での校正

**固着からの回復（Running）**: 異物が載った、湿気で局所的に値が上がった、などで delta が高いまま動かないキーを救済する。チップの Max On Duration に相当する（2026-10-03）。

- `delta >= QUIET_THRESHOLD`（静かでない）になった時点で `stuck_since` を記録し、filtered の最小・最大（`stuck_min` / `stuck_max`）の追跡を始める。指より弱い物（delta が 8〜24）でも判定が始まるよう、「静かでない」にそろえてある
- `delta < QUIET_THRESHOLD` に戻ったら追跡をやめる（回復中は delta が 0 以下になるまで続ける）
- 揺れは delta ではなく filtered で見る。回復中は baseline が動いて delta が変わるため
- 追跡中に `stuck_max - stuck_min > STUCK_VARIATION` になったら、人の指とみなして追跡をやり直す。回復中なら回復を止め、baseline はその位置のままにする。指は必ず揺れるので、長いロングトーンでも固着とは判定されない
- `now - stuck_since >= STUCK_TIME_MS` に達したら **回復** を始める
    - baseline を filtered に向けて、一定の速さ `STUCK_RECOVER_RATE`（カウント/秒）で少しずつ上げる。上げ幅は前回の更新からの実際の時間で計算する（Q8。最低 1/256 カウント）。filtered を追い越さない
    - 回復は、filtered の揺れが `STUCK_VARIATION` 以内のまま delta が 0 になるまで続ける（`QUIET_THRESHOLD` を下回っても止めない。止めると output が少し残る）
    - delta が大きいほど、0 になるまでの時間は長い（1 カウント/秒なら delta 15 で約 15 秒）。かかる時間ではなく速さで決めるのは、delta の大きさによらず、baseline の動き方をそろえるため
    - output はその速さで 0 に向かって下がる。物ならノートが止まり、もし静止した指だったとしても、音が急に切れずに弱まって消える
    - 回復中は R1〜R5 を適用しない。delta が負になったら（物を取り除いた）回復をやめ、R2・R3 に任せる
- 指を静止させたまま長く押さえると、誤って回復が始まる可能性がある。そのため `STUCK_TIME_MS` は長め（30 秒）にしている。実機で確認する（§6 の F3）
- 手をかざしたまま `STUCK_TIME_MS` 動かさなかった場合も回復が始まる。手をどければ delta が負になり、R2 で約 100ms で元に戻るので、害は小さい

**ノイズ幅（noise_floor）**

- 初期値は `NOISE_FLOOR_DEFAULT`（全キー共通）。起動時に自動で測り（§3.12）、Running の間も測り直す（§3.12 の「常時更新」）。設定画面でも測り直せる（下記）
- output は `max(0, delta - noise_floor)` とする。baseline とは独立しているので、二重に引かれることはない
- ノイズ除去（§3.3）の後の delta で測るので、フィルタを強くすれば noise_floor は小さくなる

**設定画面での校正（Calibrating）**: `SETTING_MODE` が false → true に変わった瞬間に Calibrating に入り、true → false で Running に戻る。

- **入ったとき**: `noise_floor` を全キー 0 にリセットし、固着検出の追跡をすべて解除する
- **Calibrating 中**（`BASELINE_UPDATE_INTERVAL_MS` 毎）
    - 近傍判定をせず、全キーで `baseline += (filtered - baseline) >> CALIB_SHIFT` と速く追従する
    - `CALIB_SETTLE_MS` が経過したら、`|delta|` の最大値を `noise_floor` として記録し始める（上がる方向のみ更新）
    - `noise_floor` の上限は `NOISE_FLOOR_MAX`。上限に張り付いたキーは、校正中に触れられていた可能性がある
    - output は計算する
- **出たとき**: 設定画面にいた時間が `CALIB_SETTLE_MS` より短く、`noise_floor` を記録できなかったキーは、`NOISE_FLOOR_DEFAULT` に戻す。近傍の静かさの時刻（`quiet_since`）をリセットし、`QUIET_HOLD_MS` 待ってから上方向の追従を始める
- 初期取得中に校正のスイッチが入っていたら、初期取得が終わった次のスキャンで校正に入る

設定画面ではセンサーに触れない、という運用は CLAUDE.md のとおり。

### 3.8 解析への受け渡し

信号処理と解析は、どちらも Core1 の `touch_task` の中にある（`doc/task_architecture.md` §4.1）。受け渡しはコアをまたがず、関数呼び出しで行う。

- `ElectrodeSignal::process()` の後、各キーの `output()` を `TouchTracker::set_value()` で渡す
- 受け取った後の解析は `doc/touch_analysis.md` で扱う
- PC に送るデバッグ用のフレームは raw だけで、`doc/debug_env.md` の `DEBUG_FRAMES` で Core0 の送信タスクに渡す。filtered・baseline・output は PC 側で同じ `touch_algo` に通して求める

### 3.9 デバッグ表示

- OLED の `POINT0`–`POINT5` はキー 0–5 の output を出す（2026-10-03 決定。演奏の確認に分かりやすいため）

### 3.11 実装（`crates/touch_algo` の `electrode.rs`）

ノイズ除去・基準値の計算を I2C の読み取りから切り離した、純粋な計算（no_std）。PC アプリとファームで同じコードを使う。

```rust
// K はキー毎の状態の置き場所。ファームは [ElectrodeState; TOTAL_QT_KEYS]、PC は Vec<ElectrodeState>
pub struct ElectrodeSignal<K> { pub params: Params, /* ... */ }

impl<K: AsRef<[ElectrodeState]> + AsMut<[ElectrodeState]>> ElectrodeSignal<K> {
    pub fn new(keys: K, params: Params) -> Self;
    /// now_us: 時刻（µs）、raw: キー毎の生値、valid: 読み取り成功フラグ（1 bit / キー）、
    /// calibrating: 設定画面にいるか（SETTING_MODE）
    pub fn process(&mut self, now_us: u32, raw: &[u16], valid: u128, calibrating: bool);
    pub fn state(&self) -> State;
    pub fn keys(&self) -> &[ElectrodeState];  // output()・filtered()・baseline()・delta()・noise_floor()
}
```

`process()` の流れ:

1. 読み取りに成功したキーだけ、ノイズ除去をかけて filtered を更新する（§3.3）
2. `calibrating` の立ち上がり・立ち下がりを検出して、状態を切り替える（§3.7）
3. 近傍の静かさ・大きく負の継続・固着を、全キー分判定する（§3.6, §3.7）。判定と更新を分けるのは、更新済みのキーの値で近傍判定がぶれないようにするため
4. 前回の更新から `BASELINE_UPDATE_INTERVAL_MS` 以上たっていれば、状態に応じて基準値を更新する（Acquiring: 積算、Running: R1–R5 か固着からの回復、Calibrating・AutoCalibrating: 速い追従とノイズの計測）
5. Running の間は noise_floor を測り直す（`track_noise_floor`、§3.12）
6. delta と output を計算する

ファームの `touch_task`:

- `ElectrodeSignal<[ElectrodeState; TOTAL_QT_KEYS]>` を持つ
- `process()` は解析と同じく、前の解析から `ANALYSIS_PERIOD_US`（10ms）経ったフレームで呼ぶ。§3.10 のパラメータ（移動平均のサンプル数など）は 8〜10ms 周期を前提にしているため。`debug_stream`（スキャン 2ms）では 5 スキャンに 1 回になる
- 起動直後の `TOUCH_STARTUP_SETTLE_MS`（500ms）の間は `process()` を呼ばない。チップ自身の起動時の校正（230ms 未満）が終わる前の値で初期取得しないため
- `calibrating` には `SETTING_MODE` を渡す

### 3.12 チップの境目のキーのノイズ（2026-10-27 方針。2026-10-29 touch_algo に実装、2026-11-03 ファームで有効）

`etude`（PCA9544 1 台 × 2ch、AT42QT1070 2 個、12 キー）で見つかった。

**症状**

- key5（ch 0 のチップの最後のキー）と key6（ch 1 のチップの最初のキー）は、電極が隣り合っているが、測るチップが違う。この 2 キーにだけノイズが乗り、何も触れていなくても output が 0 にならない
- key5: 常に ±5〜10 カウントのランダムな揺れがあり、ときどき +25・−15 くらいまで跳ねる
- key6: 0.4〜0.5 秒に一度、下と上に一瞬振れるスパイクが入る（±10〜20）
- ch 1 のコネクタを外すと、key5 のノイズは消える
- スキャン周期を 2 / 5 / 10 / 20ms と変えても、key6 のスパイクの間隔（約 400ms）は変わらない
- 配線をやり直した新しい基板（2026-10-29）でも同じノイズが出た。配線の不良ではない

**原因の見立て**

- 電極・配線どうしのアナログ的な結合（相互容量）で、隣のチップが測定のために加えるパルスが入っている
- チップは内蔵発振器で自走しており、互いに同期させる機能は無い。周期の差が約 2%（8ms / 400ms）あり、key5 と key6 の測定が重なる瞬間が 400ms 毎に来る（うなり）
- チップはパルスをスペクトラム拡散で出している（データシート §2.1）ので、入ってくるノイズはランダムに見える
- key5 が常に揺れていることは、電極どうしの結合だけでは説明できない。ch 1 の配線・ケーブル、または電源・GND を通って入っている可能性がある。確かめていない
- **ハードは変えられない**（2026-10-27）。ソフトで対応する。96 キーではチップの境目が 16 か所あり、境目のキーは 32 個になる

**output が 0 にならなかった仕組み**

- R3 が delta が負になるとすぐに基準値を下げ、R4 は近傍がすべて静かなときだけゆっくり上げるので、基準値はノイズの谷（下の端）に張り付き、delta は正の側に偏る
- ノイズの多いキーが「静か」の判定を何度もやり直させるので、隣のキーの基準値まで上がらなくなる

**対策（実装したもの）**

1. **下方向の追従に不感帯**（`fall_deadband`）: R3 の条件を `delta < -noise_floor` にする。基準値がノイズの谷に張り付かない。最も効いた
2. **「静か」の判定をキー毎のノイズに合わせる**（`quiet_adapt`）: `delta < QUIET_THRESHOLD + noise_floor`。境目のキーかどうかを位置で決めず、noise_floor で決める（境目以外でノイズの多いキーにも効くため）
3. **noise_floor を起動時に自動で測る**（`auto_calib_ms`、2026-10-29 決定）: 不感帯は、測った noise_floor が無いと効かない。電源を入れる度に設定画面に入らなくてよいようにする。フラッシュへの保存は、書き込みを作る必要があり、基板や環境が変わると測り直しになるので採らなかった
4. **noise_floor の常時更新**（2026-11-11）: 3 秒の計測では、その間に大きな揺れが来るかどうかが運次第で、noise_floor が 5〜16 と大きく変わったため

試して効かなかったもの: 境目のキーの AVE を 8 → 16 に上げる（2026-10-27）。ノイズは変わらないように見えた。揺れが数十〜数百 ms かけてゆっくり上下しており、1 回の測定の中の平均では減らないためと考えている。元に戻した（AVE = 8）

記録 `qubit_20261027_211117.qlog`（8ms に間引き、触っていない区間は 6〜34 秒、触った区間は 34.5〜38.5 秒）で比べた結果:

| 条件 | key5: output > 0 / ≥ 8 / 最大 | key6: output > 0 / 最大 | 触った区間のピーク（key5 / key6） |
|---|---|---|---|
| 対策なし | 90.2% / 22.3% / 17 | 79.2% / 10 | 100 / 84 |
| 自動計測のみ | 8.1% / 0% / 8 | 63.9% / 9 | 91 / 83 |
| 自動計測 + 不感帯 + 静かの判定 | 0% / 0% / 0 | 1.8% / 5 | 82 / 79 |

- 自動計測で測った noise_floor は key5 が 13、key6 が 4、他は 1〜2
- 触った区間のピークが下がるのは、基準値がノイズの谷から真ん中に上がったためで、感度が落ちたわけではない

**起動時の自動計測（`AutoCalibrating`）**

- 流れ: Acquiring（300ms）の後に `AutoCalibrating` に入り、Calibrating と同じ処理（速い追従 → `CALIB_SETTLE_MS` の後に |delta| の最大を記録）を `auto_calib_ms`（3 秒）の間行って、Running に入る。3 秒は key6 の 400ms 毎のスパイクを何回か捉えられる長さ。ファームでは起動から output が出るまで約 3.8 秒（チップの起動待ち 0.5 秒 + 初期取得 0.3 秒 + 自動計測 3 秒）
- 計測中の output は 0（起動直後にゴーストノートを出さない）
- 計測中に |delta| が `NOISE_FLOOR_MAX` を超えたキーは触れられていたとみなし、`NOISE_FLOOR_DEFAULT` に戻す
- 計測中に設定画面に入ったら、設定画面の校正に切り替わる
- PC（qubit_etude）では、接続したとき・記録を開いたとき・パラメータを変えたとき（先頭から通し直す）が「起動」に当たる。3 つの対策は「境目のノイズ対策」のスイッチで入り切りできる
- OLED: 計測が終わるまで `TOUCH_CALIBRATING`（書き手 `touch_task`、読み手 `ui_task`）が true で、起動画面（page 0）の build 日付・バージョンの代わりに `Calibrating...`（`FONT_8X13`）を 0.5 秒毎に点滅させる。`touch_algo` の状態が Running か Calibrating になったら false にし、true には戻さない

**noise_floor の常時更新（2026-11-11、`ElectrodeSignal::track_noise_floor`。スイッチにせず常に行う）**

- Running の間だけ行う。起動時の自動計測（output が 0 になり、基準値も速く追従させる）を繰り返すことはしない
- **上げる**: 毎スキャン、−delta（負の側の振れ）が今の noise_floor を超えたら、すぐにその値にする（上限 `NOISE_FLOOR_MAX`）。指が触れると delta は正の側にしか動かないので、演奏中でも指をノイズと取り違えない。境目のノイズは上下ほぼ対称なので、負の側だけでもほぼ同じ大きさが取れる
- **下げる**: `noise_track_window_ms`（5 秒）毎に、窓の中の **|delta|** の最大が今の noise_floor より小さければ 1 下げる。負の側だけで下げると、基準値がノイズの真ん中より少し下に落ち着くため、正の側との差が output に残った。指が触れた窓は下げないが、遅れるだけで害は無い。16 から 1 まで約 75 秒
- 窓は Running に入ったところから数える
- シンプルにする（2026-11-11 決定）: 指の有無で分けない、離した直後も特別に扱わない、R2 にも手を入れない
- テスト: `noise_floor_follows_noise_while_running`、`touch_does_not_raise_noise_floor`
- 記録 3 本（`qubit_20261111_225627.qlog`・`qubit_20261111_224732.qlog`・`qubit_20261027_211117.qlog`）を、通し始めを 0〜20 秒ずらして通すと、どこからでも noise_floor がほぼ同じ値（key5 が 10〜13、key6 が 6〜9）にそろい、境目のイベントは出なくなった。触れたときの効き方は変わらない
- `qubit_20261111_225627.qlog` の終わり（35.4 秒〜）に key8〜11 がそろって上がって出る Note On は残る。境目のノイズとは別のもの（原因は未確認）

**気になる点: 触れている間のノイズ（2026-11-13。すぐには対応しない、記録だけ）**

- noise_floor は一定の値を引くだけなので、触れていない間の output は 0 にできるが、触れている間は key5 のノイズがそのまま output に乗る。qubit_etude で、key5 に触れると depth（`doc/touch_analysis.md` §3.2。output の合計）が大きく揺れるのをユーザーが見た
- 電極の層に IIR（特定の電極だけ）を入れる案が出た。ただし揺れは数十〜数百 ms と遅いので、効かせるには時定数を数百 ms にする必要があり、本当に触れたときの立ち上がりも同じだけ鈍る。`doc/touch_analysis.md` §4.2 で depth の立ち上がりから触れる速さを測るので、その電極だけ速さが正しく取れなくなる
- 原因がチップの境目なら、96 キーの基板では境目のキーが各所にできる。「特定の電極」の設定では済まず、電極毎に設定を持つか、全電極に同じように効くやり方にする必要がある
- 考えられるやり方（未決）:
    1. 変化の速さで効き方を変えるフィルタ（One Euro Filter のようなもの）: 小さく遅い変化は強くならし、速く大きな変化はほとんどならさない
    2. 使う側でならす: 電極の層と depth は今のままにし、ならした値が要る所（ビブラートなど）だけ演奏情報の層でならす。速さの計測には、ならす前の depth を使う
    3. 電極毎の IIR: 境目の電極だけ時定数を長くする。いちばん簡単だが、上の副作用があり、どの電極が境目かの設定も要る
- 先に確かめること: key5 の上と、ノイズの少ない電極の上で、それぞれ指を止めて数秒触れた記録を取り、depth と position の揺れ幅・速さを比べる

## 4. 確認項目（実機）

PC（qubit_etude）での確認は済んでいる（2026-10-03）。ファームでの確認は、96 キーの新しいハードウェアができてから行う。結果は `hw96_check.md` §1 に書き込む。

| # | シナリオ | 期待する結果 |
|---|---|---|
| F1 | 何も触れずに起動し、数分放置 | ゴーストノートが出ない |
| F2 | 通常の演奏（スライド・複数点・素早い連打） | 反応が従来と同等以上。演奏中に感度が落ちていかない |
| F3 | 30 秒以上ロングトーン | 途中で音が切れない（固着と誤判定されない） |
| F4 | パッドに導電性の物を載せたまま放置 | `STUCK_TIME_MS` 後に回復が始まり、ノートが止まる |
| F5 | 約 1 秒かけてゆっくり指を近づける | 基準値が吸収して発音しない、ということが起きない |
| F6 | 設定画面に入って数秒待ち、出る | 無操作時のちらつき（OLED の POINT 表示）が減る。反応の遅れが体感で増えない |

96 キーに戻したら、全キーの raw と触ったときの delta がそろっているかも確かめる（`doc/debug_env.md` §6.2.3）。

## 5. 未決事項

- **1 周のスキャン時間**: 96 キーで実測してから、スキャン周期（`SCAN_PERIOD_US`）を 8ms にするか 10ms にするかを決める（§3.2）。10ms にすると、チップの 8ms 周期とずれて、ときどきサンプルを 1 つ飛ばす（`hw96_check.md` §2）
- **平滑化の強さ**: `SMOOTH_SAMPLES` を 2 にするか 4 にするか。ノイズの実測を見て決める
- **近傍単位の追従による偏り**: ほぼ常にどこかが触れられている演奏では、触れられていない範囲だけが追従する。リング全体が一様に温度変化する場合、演奏中の指の周辺だけ基準値が遅れる。これを問題とみなすかどうかは実機で判断する
- **固着回復と静止した指**: 指を静止させたまま長く押さえると、誤って回復が始まる可能性がある（§3.7）。F3 で確かめ、問題があれば `STUCK_TIME_MS` を延ばすか、条件を足す
- **触れている間のノイズ**（§3.12 の終わり）
