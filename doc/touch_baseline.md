# タッチセンサ信号処理（基準値の自前管理・ノイズ対策） 設計書

## 1. 背景と目的

### 1.1 現状

2026-10-01 時点（`doc/task_architecture.md` のコア・タスク構成の改修の後）。本書を書いた当初（改修前）の状態は §1.2 (c) の前提として残している。

> **（2026-10-03 追記）** 以下は `touch_algo` への置き換え（`doc/debug_env.md` の段階 4）の前の状態。置き換えで、チップの基準値（`set_reference()`）・`reference_adjust`・`Pad` の移動平均は無くなった。今は `read_touch` が生値と読み取り成功フラグ（`valid`）を返し、`touch_task` が `touch_algo` の `TouchSignal` で output を作って `QubitTouch` に渡す（§4）。12 スキャンに 1 回の読み直しによるスキャン時間の延びも無くなった

- `src/touch/read_touch.rs` は AT42QT1070 から次の 2 種類を読み、その差を入力値としている
    - Key Signal（レジスタ 4–15）: 生値
    - Reference Data（レジスタ 18–29）: チップ内部の基準値。12 スキャンに 1 回 `set_reference()` で全キー分を読み直す
- 入力値は `raw - reference - reference_adjust`（いずれも飽和減算）で、同じ Core1 の `touch_task` の中で `QubitTouch::set_value()` に渡す
- `reference_adjust` は設定画面（`SETTING_MODE == true`）にいる間、`raw - reference` の最大値を記録する。値は増える方向にしか更新されず、リセットする処理が無い
- `QubitTouch` の `Pad` が 4 サンプルの移動平均をかけてから位置を検出している（`qtouch.rs` の `MAX_MOVING_AVERAGE`）
- スキャンは `touch_task` の `Ticker` で一定周期（既定 10ms、`constants.rs` の `SCAN_PERIOD_US`）に行い、解析は 10ms 毎（`analysis_divider()`）。`debug_stream` feature では周期の既定が 2ms で、PC から 2 / 5 / 10 / 20ms に変えられる（`doc/debug_env.md`）
- 12 スキャンに 1 回の `set_reference()` で、そのスキャンだけ時間が延びる。2ms 周期では周期を超える（`doc/debug_env.md` §6.1 の実測）

### 1.2 問題点

**(a) チップの基準値が追従しない**

データシート（`doc/Atmel-9596-AT42-QTouch-BSW-AT42QT1070_Datasheet.pdf`）を見ると、チップの基準値は「ボタンの ON/OFF 判定」を目的に作られており、QUBIT のように差分の大きさを連続量として使う用途には合わない。

| 項目 | データシートの記述 | QUBIT への影響 |
|---|---|---|
| ドリフト速度（§2.11.1） | タッチ方向へ 1 カウント / 2.88 秒、反対方向へ 1 カウント / 0.96 秒 | 数十カウントのずれを吸収するのに数十秒〜数分かかる |
| Drift Hold Time（§2.11.6） | 1 キーでも検出中なら、同じチップの全キーでドリフトが止まる。離してから約 4 秒は止まったまま | 演奏中は 6 キーのどれかが触れられていることが多く、基準値がほぼ固定になる |
| 検出しきい値 NTHR | 既定 20 カウント。検出中のキーはドリフトしない | こちらの判定（`TOUCH_THRESHOLD = 32`、隣接比較）とずれるため、いつ止まり、いつ動くのかを外から予測できない |
| Max On Duration（§2.11.4） | `init()` で 0（無効）にしている | 検出状態のまま固まったキーが二度と再校正されない |
| Positive Recalibration（§2.11.5） | 生値が基準値より 4 カウント以上下がると即座に再校正 | 下方向の追従は速いので、この挙動は自前実装でも踏襲する |

加えて、チップ側で基準値が上がると `reference_adjust` の固定オフセットと二重に引かれ、その分だけデッドゾーンが広がる。

**(b) ノイズが多い**

これまでの経験から、生値にはかなりのノイズが乗っている。本書を書いた時点では、`qtouch.rs` の `Pad` の 4 サンプル移動平均（改修前は Core0 で動いていた）と、単発スパイク除去（`SINGLE_PAD_SPIKE_*`）で対処していた。移動平均は `touch_algo` のノイズ除去（§3.3）に置き換えて外した（2026-10-03。§4.6）。スパイク除去は残している。

**(c) 触れる速さを取る土台が無い**

（以下の周期と OLED の問題は、改修前の構成でのもの。`doc/task_architecture.md` の改修で、スキャンは Core1 で一定周期になり、OLED は Core0 の I2C0 に移って解消した。残っているのは、`QubitTouch` の時間の計算が「10ms 毎に呼ばれる」前提のままであること）

今後、「どれだけ速く触れたか（少しずつ値が増えたのか、急に大きくなったのか）」を取りたい。速さの判定そのものは `qtouch.rs` 側の仕事だが、今の信号の渡し方では時間の情報が失われている。

- 1.1 のとおり、チップ（8ms）・Core1（不定）・Core0（約 10ms）がそれぞれ独立した周期で動いている。同じ値を 2 回読んだり、1 サンプル飛ばしたりする
- 1 周期ごとの値に時刻の情報が付いていないため、Core0 からは値がいつ測られたものか分からない
- OLED への転送（1024 バイト、31 バイトずつ 34 回の I2C 書き込み）は 400kHz で約 25ms かかると見積もられる。100ms 毎の転送の間、タッチのスキャンが止まる（実測はまだしていない）

（2026-10-03 追記）速さの計測は信号処理の層では行わず、`QubitTouch` の側で行うことにした（§1.4 方針 4、§3.8）。信号処理の側で用意するのは、一定周期で時刻のそろった output までとする

### 1.3 AT42QT1070 の測定タイミング（データシートより）

- 約 8ms の固定サイクルで動作する（§2.5）。LP_MODE（レジスタ 54）が 0 または 1 なら毎サイクル（8ms 毎）に測定する。現在の `init()` は LP_MODE = 0 に設定しているので、すでに最速で動いている
- Averaging Factor（AVE、レジスタ 39–45。既定 8）を大きくすると S/N は良くなるが、測定時間が延びる。全キーの測定が 8ms を超えると、ステータス（レジスタ 2）の OVERFLOW ビットが立ち、サイクルが延びる（§2.5, §5.4）
- 16 個のチップはそれぞれ自走しており、互いに同期していない。PCA9544 は I2C の経路を切り替えるだけなので、各キーの生値はおよそ 8ms 毎に更新される
- 同期していないため、チップの境目の隣り合うキーに、隣のチップの測定によるノイズが入る（§3.12）

したがって、**生値の時間分解能は 8ms が上限**になる。

- **実測では 10ms 前後に見えた**（2026-10-03、6 キー直結、2ms 周期で qubit_etude の「値の更新間隔」のヒストグラム）。原因は確かめていない。使っていない key6 も既定の AVE = 8 で測定していて、全キーの測定が 8ms を超えていた可能性がある
- そこで `init()` で key6 を無効にした（AVE/AKS のレジスタ 45 に 0 を書く。データシート §2.3 の「使わないキーは AVE を 0 にする」）。効果の測定はしないことにしたが、無効にした後のヒストグラムでは 8ms の山がいちばん強く見えた（同日、目視）。96 キーでは 1 周に 8ms 前後かかり、チップの更新が 8ms でも 10ms でも得られる分解能はほとんど変わらないため、正確な更新周期にはこだわらない

### 1.4 方針

1. チップからは **生値（Key Signal）だけ** を読み、基準値はファームウェアでキーごとに管理する
2. ノイズ除去は信号処理（`read_touch` 側）で行う。移動平均を信号処理と `qtouch` の二重にかけないようにする
3. スキャンは `doc/task_architecture.md` の改修で **一定周期** になり、スキャン → 信号処理 → 解析（`qtouch`）が Core1 の `touch_task` の中でひと続きに行われる。本書の信号処理は、その間に入る
4. **速さ（ベロシティ）の検出は信号処理では扱わない**（2026-10-03 決定）。生値は自由に上下するので、キー毎の値から立ち上がりを決めるのは難しい。`QubitTouch` の高度なタッチ判定の側で計測する。設計は別の設計書で扱う（§3.8, §7）
5. **ゆっくり触れても、基準値に吸収されずに反応すること** を優先する。ノイズ除去による遅れと鈍りは、速く触れたときの立ち上がりを鈍らせるが、それは許容する
6. 基準値の追従規則・速度・停止条件、フィルタの強さはすべて `const` で調整できるようにする
7. 基準値とノイズ幅（デッドゾーン）を別の量として管理し、二重に引かれないようにする

## 2. 用語

| 用語 | 意味 |
|---|---|
| raw | AT42QT1070 の Key Signal。指が近づくと値が増える |
| filtered | raw にノイズ除去（§3.3）をかけた値 |
| baseline | 未タッチ時の filtered の推定値。本設計で自前管理する |
| delta | `filtered - baseline`（符号付き）。正がタッチ方向 |
| noise_floor | 未タッチ時の delta の揺れ幅。出力から差し引くデッドゾーン |
| output | `max(0, delta - noise_floor)`。解析（`QubitTouch`）に渡す値 |
| 近傍 | リング上で自キーから ±`NEIGHBOR_RANGE` 以内のキー（`TOTAL_QT_KEYS` で折り返す） |

キー番号はすべて `TOUCH_INDEX_SHIFT` で回転した後のインデックス（`shifted_index`）で扱う。こうすると、近傍がリング上の物理的な隣と一致する。→ 2026-10-24 に新しい設計のハードウェアに合わせて回転をやめ、読み取り順のインデックスがそのままリング上の並びになった（`debug_env.md` §1.2）。

時間に関する定数は、すべて **ミリ秒で定義** する。スキャン周期を変えても意味が変わらないようにするため。

## 3. 仕様

### 3.1 信号処理の流れ

```
[Core1: touch_task]
  AT42QT1070 (8ms 周期で自走)
    │ I2C 読み取り（scan_period_us() 毎）
    ▼
  raw（hi/lo ずれは読み直し済み）──► スパイク除去（3 点メディアン）──► 平滑化（短い移動平均）──► filtered
                                                                                              │
                                   baseline（§3.4–3.7、BASELINE_UPDATE_INTERVAL_MS 毎に更新）◄┤
                                                                                              ▼
                                                        delta = filtered - baseline ──► output
    │ 関数呼び出しで渡す（同じタスクの中。コアはまたがない）
    ▼
  QubitTouch（qtouch.rs）: 位置検出・追跡・ノート変換・速さの計測（別設計書）（Pad の移動平均は外す）
    │ ノートイベント
    ▼
  MIDI_TX ──► Core0: midi_tx_task
```

### 3.2 スキャン周期

- Core1 のスキャンループを `Ticker` で **`scan_period_us()` 毎**（既定値は `constants.rs` の `SCAN_PERIOD_US`）に回す。サンプル間隔が一定になり、フィルタの係数や傾きの計算が時間として意味を持つ
- スキャン周期はチップのサイクル（8ms）以上にする（`debug_stream` で 2ms にするのは、チップの更新を観察するため）。8ms より速く読んでも、同じ値を重複して読むだけになるため
- 1 周のスキャン時間は、見積もりでは 1 チャンネルあたり約 0.5ms × 16 チャンネル ≒ 8ms 前後。これを **実測** し、スキャン周期を決める（8ms か 10ms の想定。今の既定は 10ms）
- OLED 転送（約 25ms と見積もり）がスキャンを止める問題は、`doc/task_architecture.md` で OLED を Core0 の I2C0 に移すことで解消する。周期化もそちらの段階 5 で行う
- 周期に間に合わなかった場合（`Ticker` の遅れ）でも、フレームの時刻は実際にスキャンした時刻を記録する

### 3.3 ノイズ除去

キーごとに、次の順で処理する。

1. **hi/lo ずれ補正**: ファームの `read_touch` で、前回値との差が 220（`HI_LO_REREAD_DIFF`）以上のキーだけ、その場で読み直す（2026-10-02 決定・実装済み）
    - 原因: AT42QT1070 は 16bit の値の 2 バイトをまとめて固定しない（データシート 4.3.2 の Note）。上位を読んでから下位を読むまでの間にチップが値を更新し、値が 256 の境目をまたぐと、約 ±256 ずれた値が読める。ずれるのはその 1 回の読み込みだけで、チップのレジスタは正しい
    - 次の更新は 8ms 後なので、すぐ読み直せば正しい値が得られる。本当に大きく変化したときは同じ値が読めるだけで、値を誤らない。上向き・下向きのどちらのずれにも効く
    - 読み直しはずれたキー 1 つだけ（`At42Qt1070::read_1key`）。ずれるのは更新の瞬間に読んでいたキーだけなので、6 キーまとめて読み直す必要は無い
    - 読み直しに失敗したら前回の値を使う
    - 以前の対策（前回値より 200 以上大きければ 256 を引く）は廃止した。上向きしか直せず、本当に 200 以上上がったときも 256 引いてしまうため
    - PC 側（`touch_algo` と qubit_etude）の以前の規則による補正も外した。ファームが正しい値を送るので要らない。以前に記録した `.qlog` を再生すると、ずれはスパイクのまま見える（3 点メディアンで filtered からは取り除かれる）
2. **スパイク除去**: 直近 3 サンプルのメディアン。単発のスパイクを取り除く。遅れは 1 サンプル
3. **平滑化**: 直近 `SMOOTH_SAMPLES` サンプル（初期値 2〜4）の移動平均。遅れは (N−1)/2 サンプル

速さへの影響を次の表に示す（スキャン周期 8ms の場合）。

| 構成 | 合計の遅れ | 立ち上がりの鈍り |
|---|---|---|
| メディアン 3 + 平均 2 | 約 12ms | 小 |
| メディアン 3 + 平均 4 | 約 20ms | 中（現状の `Pad` の平均 4 と同程度） |

- 遅い方向（数十〜数百 ms かけた立ち上がり）の計測には、どちらの構成でもほとんど影響しない
- 速い方向（1〜2 サンプルで立ち上がる）は平滑化で鈍る。`QubitTouch` で速さを計測するときの制約になる（方針 4・5）
- `qtouch.rs` の `Pad` の移動平均（`MAX_MOVING_AVERAGE` = 4）は二重になるため外す（1 にする）。`qtouch.rs` の単発スパイク除去（空間方向）は目的が違うので残す
- 読み取りに失敗したサンプルは、フィルタの履歴に入れない（前回の filtered をそのまま使う）

### 3.4 基準値のデータ構造（キーごと）

| フィールド | 型 | 内容 |
|---|---|---|
| `baseline_q` | `u32` | 基準値の固定小数点表現（Q8、`filtered << 8` 相当）。遅い追従が丸め誤差で消えないようにする |
| `noise_floor` | `u16` | デッドゾーン |
| `quiet_since` | `Instant` | 近傍が静かになった時刻 |
| `neg_since` | `Option<Instant>` | delta が大きく負になり始めた時刻（即時再校正用） |
| `stuck_since` | `Option<Instant>` | delta が `QUIET_THRESHOLD` 以上（静かでない）になり始めた時刻（固着検出用。§3.7） |
| `stuck_min` / `stuck_max` | `u16` | 固着検出区間の filtered の最小・最大 |
| `recovering` | `bool` | 固着からの回復中か |

フィルタの履歴（キーあたり数サンプル）を合わせても、96 キーで数 KB に収まる。`TouchSignal` は Core1 の `touch_task`（静的に確保される future）の中に置くため、スタックへの影響は小さい（§4.4）。

実装（`crates/touch_algo` の `KeyState`）では、時刻を `Instant` ではなく u32 の µs で持ち（`Option<u32>`）、`quiet_since` も `Option<u32>` にした。ほかに初期取得の積算（`acquire_sum` / `acquire_count`）や、noise_floor を計り始めたか（`noise_measured`）を持つ（`doc/debug_env.md` §4.6）。

全体の状態として、次を持つ。

- `state`: `Acquiring`（初期取得中）/ `Running`（通常）/ `Calibrating`（設定画面中）/ `AutoCalibrating`（起動時の noise_floor の自動計測中。§3.12）
- `last_update`: 基準値を最後に更新した時刻
- `prev_work_mode_display`: 設定画面に入った瞬間を検出するための前回値（実装では `prev_calibrating`。`process()` の `calibrating` の前回値）

### 3.5 初期取得（Acquiring）

1. 起動後 `ACQUIRE_MS` の間、キーごとに filtered を積算する
2. 平均値を `baseline_q` の初期値にする
3. 取得中の output は全キー 0 とする（`QubitTouch` にタッチとして見えないようにする）
4. 読み取りに失敗したサンプルは積算から除外し、成功回数で割る。1 回も成功しなかったキーは、次に読めたときの filtered をそのまま初期値にする

起動時に触れていた場合、そのキーの baseline は高めに取得される。指を離すと delta が大きく負になるので、§3.6 の下方向の速い追従で自動的に回復する。

### 3.6 基準値の追従規則（Running）

`BASELINE_UPDATE_INTERVAL_MS` 毎に、キーごとに上から順に判定して、最初に当てはまった規則を適用する。

| # | 条件 | 動作 | 意図 |
|---|---|---|---|
| R1 | 読み取り失敗中（前回値を流用している） | 更新しない | 古い値で基準値を動かさない |
| R2 | `delta < -NEG_RECAL_THRESHOLD` が `NEG_RECAL_MS` 以上続いた | `baseline = filtered`（即時再校正） | チップの Positive Recalibration 相当。起動時タッチ・急な環境変化からの復帰 |
| R3 | `delta < 0` | `baseline += (filtered - baseline) >> FALL_SHIFT` | 下方向は速めに追従 |
| R4 | 近傍が静かで、その状態が `QUIET_HOLD_MS` 以上続いている | `baseline += (filtered - baseline) >> RISE_SHIFT`。ただし 1 回の上昇は `RISE_MAX_STEP_Q` まで | 上方向（タッチ方向）はゆっくり追従。上限を付けて、手をかざしたままでも吸収速度を抑える |
| R5 | それ以外（近傍が触れられている） | 更新しない | 演奏中のタッチを基準値に取り込まない |

**「近傍が静か」の定義**

- 自キーと近傍の全キーで `delta < QUIET_THRESHOLD`
- 近傍を含めるのは、指の周辺のキーも近接で raw が上がるため。自キーだけで判定すると、指の周辺キーの基準値が少しずつ上がってしまう
- 近傍が一度でも静かでなくなったら `quiet_since` をリセットする（チップの Drift Hold Time の考え方を、チップ単位ではなく近傍単位にしたもの）

**ゆっくりしたタッチを吸収しないための制約**

ゆっくり近づく指は、基準値から見ると「ゆっくり上がるドリフト」と見分けがつかない。ゆっくり触れても反応するよう、次を満たすようにパラメータを決める。

- 想定する最も遅いタッチ（`SLOWEST_ATTACK_MS` かけて、発音に必要な delta まで上がる。ここでは仮に 24 とする）の間に、基準値が上がる量が `QUIET_THRESHOLD / 2` 以下であること
- R4 で上がり得る量の上限は「`QUIET_THRESHOLD` を下回っている時間 × 上昇速度の上限」。上昇速度の上限は `RISE_MAX_STEP_Q / 256` カウント ÷ `BASELINE_UPDATE_INTERVAL_MS` で決まる
- 例: `SLOWEST_ATTACK_MS` = 1000ms、`QUIET_THRESHOLD` = 8 なら、`QUIET_THRESHOLD` 未満の区間はおよそ 1000 × 8/24 ≒ 330ms。上昇速度の上限を 3 カウント/秒とすると、吸収されるのは約 1 カウントで、条件（4 以下）を満たす
- さらに `QUIET_HOLD_MS` の待ちがあるため、直前まで演奏していた場所ではこの吸収は起きない

### 3.7 固着からの回復・ノイズ幅・設定画面での校正

**固着からの回復（Running）**: 異物が載った、湿気で局所的に値が上がった、などで delta が高いまま動かないキーを救済する。チップの Max On Duration に相当する。2026-10-03 に次のように改めた（P4 の確認で見つかった問題への対応）。

- 以前は `delta >= ACTIVE_THRESHOLD`（24）で固着の判定を始めていた。指より弱い物を載せて delta が 8〜24 に留まると、「静か」でもなく固着の判定も始まらないので R5（更新しない）のままになり、baseline がいつまでも動かなかった。近傍のキーも「静か」にならないので、上方向の追従が止まる
- そこで、判定の開始を「静かでない」（`delta >= QUIET_THRESHOLD`）にそろえ、`ACTIVE_THRESHOLD` は廃止した。回復も、一気に baseline を合わせず、時間をかけて少しずつ上げるようにした

規則:

- `delta >= QUIET_THRESHOLD` になった時点で `stuck_since` を記録し、filtered の最小・最大（`stuck_min` / `stuck_max`）の追跡を始める
- `delta < QUIET_THRESHOLD` に戻ったら追跡をやめる（回復中は delta が 0 以下になるまで続ける）
- 揺れは delta ではなく filtered で見る。回復中は baseline が動いて delta が変わるため
- 追跡中に `stuck_max - stuck_min > STUCK_VARIATION` になったら、人の指とみなして追跡をやり直す（`stuck_since` を現在時刻に、min/max を現在の filtered にする）。回復中なら回復を止め、baseline はその位置のままにする。指は必ず揺れるので、長いロングトーンでも固着とは判定されない
- `now - stuck_since >= STUCK_TIME_MS` に達したら **回復** を始める
    - baseline を filtered に向けて、一定の速さ `STUCK_RECOVER_RATE`（カウント/秒）で少しずつ上げる。`BASELINE_UPDATE_INTERVAL_MS` 毎の上げ幅は `STUCK_RECOVER_RATE × 256 × 前回の更新からの実際の時間 / 1 秒`（Q8。最低 1/256 カウント）。更新は 8ms 毎のスキャンに合わせて約 24ms 毎になるので、設定の周期ではなく実際の時間で計算する。filtered を追い越さない
    - 回復は、filtered の揺れが `STUCK_VARIATION` 以内のまま delta が 0 になるまで続ける（`QUIET_THRESHOLD` を下回っても止めない。止めると残りを R4 のゆっくりした追従に任せることになり、output が少し残る）
    - delta が大きいほど、0 になるまでの時間は長い（1 カウント/秒なら delta 15 で約 15 秒）。かかる時間ではなく速さで決めるのは、delta の大きさによらず、baseline の動き方をそろえるため
    - output はその速さで 0 に向かって下がる。物ならノートが止まり、もし静止した指だったとしても、音が急に切れずに弱まって消える
    - 回復中は R1〜R5 を適用しない（回復の上げ幅で動かす）。delta が負になったら（物を取り除いた）回復をやめ、R2・R3 に任せる
- Violin モードで指を静止させたまま長く押さえると、誤って回復が始まる可能性がある。そのため `STUCK_TIME_MS` は長め（30 秒程度）から始め、実機で確認する。必要なら「固着回復は Piano モードのみ」とする
- 手をかざしたまま `STUCK_TIME_MS` 動かさなかった場合も回復が始まる。手をどければ delta が負になり、R2 で約 100ms で元に戻るので、害は小さい

**ノイズ幅（noise_floor）**

- 初期値は `NOISE_FLOOR_DEFAULT`（全キー共通）
- 設定画面で計測し直す（下記）
- output は `max(0, delta - noise_floor)` とする。baseline とは独立しているので、二重に引かれることはない
- ノイズ除去（§3.3）の後の delta で測るので、フィルタを強くすれば noise_floor は小さくなる

**設定画面での校正（Calibrating）**: `SETTING_MODE`（旧 `WORK_MODE_DISPLAY`）が false → true に変わった瞬間に Calibrating に入り、true → false で Running に戻る。

- **入ったとき**
    - `noise_floor` を全キー 0 にリセットする
    - 固着検出の追跡をすべて解除する
- **Calibrating 中**（`BASELINE_UPDATE_INTERVAL_MS` 毎）
    - 近傍判定をせず、全キーで `baseline += (filtered - baseline) >> CALIB_SHIFT` と速く追従する
    - `CALIB_SETTLE_MS` が経過したら、`|delta|` の最大値を `noise_floor` として記録し始める（上がる方向のみ更新）
    - `noise_floor` の上限は `NOISE_FLOOR_MAX`。上限に張り付いたキーは、校正中に触れられていた可能性がある
- **出たとき**
    - 設定画面にいた時間が `CALIB_SETTLE_MS` より短く、`noise_floor` を記録できなかったキーは、`NOISE_FLOOR_DEFAULT` に戻す

CLAUDE.md にある「設定画面ではセンサーに触れない」という運用は、そのまま維持する。

### 3.8 立ち上がり開始時刻（onset）— 廃止（2026-10-03 決定）

以前の版では、速さ検出の土台として、キー毎に「静かな状態から delta が上がり始めた時刻」（onset）を信号処理の側で記録することにしていた。これを廃止する。

- 生値は自由に上下するので、キー 1 つの delta から立ち上がりの始まりを決めるのは難しい。演奏の速さは、複数のキーからタッチ位置を求め、追跡している `QubitTouch` の高度なタッチ判定の側で計測すべきである（§1.4 方針 4）
- 信号処理（`touch_algo`）は output を作るところまでとし、速さに関わる情報は出さない
- `touch_algo` の onset の記録・`ONSET_MARGIN`、qubit_etude の onset の表示（印・しきい値の横線・パラメータ）は削除した（2026-10-03）

### 3.9 解析（QubitTouch）への受け渡し

信号処理と解析は、どちらも Core1 の `touch_task` の中にある（`doc/task_architecture.md` §4.1）。受け渡しはコアをまたがず、関数呼び出しで行う。

- `TouchSignal::process()` が返す `output` を、従来どおり `QubitTouch::set_value()` で渡す
- PC に送るデバッグ用のフレームは raw だけで、`doc/debug_env.md` の `DEBUG_FRAMES` で Core0 の送信タスクに渡す。filtered・baseline・output は PC 側で同じ `touch_algo` に通して求める（ファームの計算結果を送る PROC は見送った。`doc/debug_env.md` §6）

### 3.10 デバッグ表示

- デバッグ表示用の `POINT0`–`POINT5` はキー 0–5 の output を出す（2026-10-03 決定。演奏の確認に分かりやすいため。切り替えの `const` は設けない）
- 1 周のスキャン時間は、`task_architecture.md` で追加した OLED の診断ページ（`SCAN_TIME` の最小・平均・最大）で確認できる

### 3.12 チップの境目のキーのノイズ（2026-10-27 方針。2026-10-29 touch_algo に実装、ファームでは未使用）

`etude`（PCA9544 1 台 × 2ch、AT42QT1070 2 個、12 キー）で 12 キーが読めるようになったところで見つかった。

**症状**

- key5（ch 0 のチップの最後のキー）と key6（ch 1 のチップの最初のキー）は、電極が隣り合っているが、測るチップが違う。この 2 キーにだけノイズが乗り、何も触れていなくても output が 0 にならない
- key5: 常に ±5〜10 カウントのランダムな揺れがあり、ときどき +25・−15 くらいまで跳ねる。delta が `QUIET_THRESHOLD`（8）をたびたび超える
- key6: 0.4〜0.5 秒に一度、下と上に一瞬振れるスパイクが入る（±10〜20）。それ以外の時間は落ち着いているが、raw がいつも baseline より 5 くらい上にあり、output が 1〜4 残る
- ch 1 のコネクタを外すと、key5 のノイズは消える
- スキャン周期を 2 / 5 / 10 / 20ms と変えても、key6 のスパイクの間隔（約 400ms）は変わらない

**原因の見立て**

- 電極・配線どうしのアナログ的な結合（相互容量）で、隣のチップが測定のために加えるパルスが入っている。同じチップの中ではキーを 1 つずつ測るので、隣どうしでもこうした揺れは起きにくい（と考えている）
- チップは内蔵発振器で自走しており、互いに同期させる機能は無い（データシートに見当たらない）。周期の差が約 2%（8ms / 400ms）あり、key5 と key6 の測定が重なる瞬間が 400ms 毎に来る（うなり）。スキャン周期を変えても間隔が変わらないので、こちらの読み取りのタイミングとは関係ない
- チップはパルスをスペクトラム拡散で出している（データシート §2.1）ので、入ってくるノイズはランダムに見える
- key5 が常に揺れていることは、電極どうしの結合だけでは説明できない（それならうなりになるはず）。ch 1 の配線・ケーブル、または電源・GND を通って入っている可能性がある。確かめていない
- **ハードは変えられない**（2026-10-27）。ソフトで対応する。96 キーではチップの境目が 16 か所あり、境目のキーは 32 個になる

**output が 0 にならない仕組み**

ノイズの量そのものに加えて、§3.6 の追従規則が、ノイズを正の output に変えている。

- R3 は delta が負になるとすぐに基準値を下げる。R4 は近傍がすべて `delta < QUIET_THRESHOLD` の状態が `QUIET_HOLD_MS` 続いたときだけ、ゆっくり上げる
- そのため、基準値はノイズの谷（下の端）に張り付き、delta は平均でノイズの振れ幅の半分くらい正の側に偏る。output = delta − noise_floor が 0 にならない
- key5 は何度も `QUIET_THRESHOLD` を超えるので、key5 を近傍に含む key3〜7 の「静か」の判定が、そのたびにやり直しになる。ノイズの多いキー 1 つで、隣のキーの基準値まで上がらなくなる
- 設定画面で校正しても、noise_floor の上限（`NOISE_FLOOR_MAX` = 16）は key5 のスパイク（約 25）より小さい。また Running に戻ると、基準値は再び谷へ下がっていく。校正だけでは解決しない

**対策**（効きそうな順。この順で試す）

1. **境目のキーの AVE を上げる**（チップの設定）
    - 各チップの key0 と key5 の AVE（レジスタ 39 と 44）を、既定の 8 から 16 または 32 にする
    - 隣のチップから入るノイズはランダムなので、チップの中で平均する回数を増やせば減るはず。ノイズを元から減らせるのはこれだけで、こちらの信号処理の遅れも増えない
    - 境目のキーは、チップの中のキー番号（key0・key5）で決まる
    - 確かめること: ノイズの減り方。更新間隔が 8ms のままか（qubit_etude の「値の更新間隔」のヒストグラム、ステータスの OVERFLOW ビット。§1.3）。AVE を変えたキーで、raw のレベルや触ったときの delta が変わらないか（キー毎の感度がずれると、`QubitTouch` の位置の計算に影響する）
    - **結果（2026-10-27）: 効果無し**。各チップの key5（key5・key11）の AVE を 16 にしたが、ノイズは全く変わらないように見えた。変更は元に戻した（AVE = 8）。書き込みが効いていたかは、レジスタを読み返して確かめてはいない
    - 効かなかった理由の見立て: key5 の揺れは数十〜数百 ms かけてゆっくり上下しており、AVE の平均（1 回の測定の中の短い時間）では減らない。2 つのチップの周期のずれで、測定と隣のチップのパルスとの重なり方が少しずつ変わり、1 回の測定の中ではほぼ同じだけノイズが入るためと考えている。AVE を 32 にしても効かない見込み
    - このため、対策は 2・3（`touch_algo`）が中心になる。ノイズが遅いので、メディアンや短い移動平均では消えない。基準値が谷に張り付かないようにすることと、そのキーの noise_floor を実際のノイズに合わせることが中心になる
2. **下方向の追従に不感帯を入れる**（全キー共通）
    - R3 の条件を `delta < 0` から `delta < -noise_floor` に変える。`-noise_floor <= delta < 0` は更新しない
    - 基準値がノイズの谷に張り付かないようにする。output が 0 にならない直接の原因なので、1 の結果によらず入れる
    - これだけでは、谷にいる基準値を上げるのは R4 のままなので、3 の「静か」の判定の見直しと合わせて効く
    - 影響: 起動時のタッチからの戻り（P2）は R2 が受け持つので変わらない見込み。下向きの環境変化への追従（P6）は noise_floor の分だけ残る
3. **キー毎のノイズの量に合わせる**
    - 「静か」の判定を、キー毎に `delta < QUIET_THRESHOLD + noise_floor` にする（案）。ノイズの多いキーが、自分と近傍の上方向の追従を止めないようにする
    - `NOISE_FLOOR_MAX`（16）を見直す。上げると、そのキーの output から引く量が増えて感度が下がる
    - key6 のような一瞬のスパイクには、メディアンを 5 点にする（遅れが 1 サンプル増える）などを考える。境目のキーだけにするか、全キーにするかは記録を見て決める
    - 境目のキーかどうかを位置で決めず、校正で測った noise_floor で決める。境目以外でノイズの多いキーにも効くため
    - 注意: noise_floor が大きいキーは output が小さくなり、`QubitTouch` の位置の計算で隣のキーより弱く見える。どの程度問題になるかを確かめる

**PC での試験（2026-10-27）**

- 記録: `qubit_20261027_211117.qlog`（`etude`、2ms 周期。最初の約 34 秒は触っていない。その後 key5〜7 を触った。240 秒で I2C1 が固まり、以降は読めていない）
- 既定のパラメータのままのファームで、触っていない区間に、位置 5.1〜5.4（key5 と key6 の間）の Note On/Off が 0.5〜1 秒に 1 回くらい出ていた
- 比べ方: worktree（ブランチ `exp_boundary_noise`）の touch_algo に、R3 の不感帯（`fall_deadband`）と「静か」の判定を noise_floor で上げる規則（`quiet_adapt`）をスイッチとして足し、`tools/qubit_etude/examples/boundary_eval.rs` で記録を 8ms に間引いて通した。校正ありは、記録の 1〜4 秒に設定画面に入ったものとして扱った。触っていない区間（6 秒〜）の output と、触った区間の output のピークを見た。ノートの出方は PC では再現できないので、`TOUCH_THRESHOLD`（8）以上になった割合を目安にした

| 条件 | key5: output > 0 / ≥ 8 / 最大 | key6: output > 0 / 最大 | 触った区間のピーク（key5 / key6） |

| A 今のまま（校正なし） | 87.5% / 16.2% / 16 | 63.1% / 7 | 103 / 84 |

| H 校正なし + 不感帯 + 静かの判定 | 58.0% / 3.2% / 13 | 3.2% / 5 | 98 / 81 |

- 校正で測った noise_floor は key5 が 10、key6 が 4、他は 1〜2。`NOISE_FLOOR_MAX` を 32 にしても結果は同じ（16 に届いていない）。平滑化を 4 にしても、ほとんど変わらない
- **R3 の不感帯（対策 2）が最も効く**。基準値が谷に張り付かなくなり、key6 も 0 に近づく。触った区間のピークが下がるのは、基準値がノイズの谷から真ん中に上がったためで、感度が落ちたわけではない
- 「静か」の判定を noise_floor で上げる規則（対策 3）は、key6 で少し効くだけ
- **校正が要る**。校正しないと noise_floor が既定の 4 のままで、key5 のノイズ（10 くらい）を引ききれない（H）。今は noise_floor を保存しないので、電源を入れる度に設定画面に入る必要がある（§7 の「noise_floor の保存」）
- 記録は 1 つ（34 秒）だけで、校正の区間も 3 秒と短い。key6 の 400ms 毎のスパイクを、校正で捉えきれていない可能性がある

**進め方**

1. 対策 1 を試すコードを入れ、実機でノイズを測る
2. 残ったノイズを qubit_etude で記録（.qlog）し、対策 2・3 を `replay_algo` と PC アプリで調整する。パラメータを変えたら P1〜P9（§6.1）も見直す
3. 決まったら `touch_algo` に入れ、ファームで確かめる

**作り直した基板での確認（2026-10-29）**: 配線をやり直した新しい基板でも、key5・key6 に同じノイズが出た。配線の不良ではなく、上の「原因の見立て」のとおりチップどうしの結合によるものと考えてよい。

**noise_floor の自動計測（2026-10-29 決定。同日 touch_algo に実装）**

R3 の不感帯は、校正で測った noise_floor が無いと効かない（上の表の H）。電源を入れる度に設定画面に入らなくてよいよう、起動時に自動で測る（案 C）。比べた案は次のとおり。

- A: 今のまま設定画面で校正する。操作を忘れると効かない
- B: 校正した noise_floor をフラッシュに保存する。書き込みを作る必要があり、基板や環境が変わると測り直しになる
- **C（採用）**: 起動後の数秒、触れていない前提で自動的に測る。設定画面での校正はそのまま残し、測り直しに使う

実装したこと（`Params` の `auto_calib_ms` > 0 のとき）:

- 流れ: Acquiring（300ms）の後に状態 `AutoCalibrating` に入り、Calibrating と同じ処理（速い追従 → `CALIB_SETTLE_MS` の後に |delta| の最大を記録）を `auto_calib_ms` の間行って、Running に入る。測る時間は、key6 の 400ms 毎のスパイクを何回か捉えられる長さとして 3 秒とする（2026-10-29 決定。測るのは settle を除いた 2.5 秒）。ファームでは起動から output が出るまで約 3.8 秒（チップの起動待ち 0.5 秒 + 初期取得 0.3 秒 + 自動計測 3 秒）になり、その間は触っても音が出ない。短くできるかは、qubit_etude で値を変えて noise_floor が変わらないかで確かめられる
- 計測中の output: Acquiring と同じく 0（起動直後にゴーストノートを出さない）
- 起動時に触れていた場合: 計測中に |delta| が `NOISE_FLOOR_MAX` を超えたキーは触れられていたとみなし、`NOISE_FLOOR_DEFAULT` に戻す。設定画面での校正では、これまでどおり上限に張り付いたままにする
- 計測中に設定画面に入ったら、設定画面の校正に切り替わる（自動計測はそこで終わる）
- 不感帯（`fall_deadband`）と「静か」の判定（`quiet_adapt`）もスイッチにした。3 つとも既定は使わない設定で、ファームの動作は変わらない。PC で確かめてから、ファームで使うかを決める

確かめ方: qubit_etude も同じ `touch_algo` を使うので、PC で動作を体験できる。アルゴリズムの欄の「境目のノイズ対策」で 3 つのスイッチを入り切りする。PC では、接続したとき・記録を開いたとき・パラメータを変えたとき（先頭から通し直す）が「起動」に当たり、その最初の数秒で noise_floor が測られる（状態が「自動計測中」になる）

記録 `qubit_20261027_211117.qlog` で比べた結果（8ms に間引き、触っていない区間は記録の 6〜34 秒、触った区間は 34.5〜38.5 秒）:

| 条件 | key5: output > 0 / ≥ 8 / 最大 | key6: output > 0 / 最大 | 触った区間のピーク（key5 / key6） |
|---|---|---|---|
| 今のまま | 90.2% / 22.3% / 17 | 79.2% / 10 | 100 / 84 |
| 自動計測のみ | 8.1% / 0% / 8 | 63.9% / 9 | 91 / 83 |
| 自動計測 + 不感帯 + 静かの判定 | 0% / 0% / 0 | 1.8% / 5 | 82 / 79 |

自動計測で測った noise_floor は key5 が 13、key6 が 4、他は 1〜2。設定画面で校正したときの結果（上の表の E）とほぼ同じになった

### 4.2 `TouchSignal`（`crates/touch_algo`）

ノイズ除去・基準値の計算を I2C の読み取りから切り離した、純粋な計算のクレート（no_std）。PC アプリとファームで同じコードを使う。API は次のとおり（実装済み）。

```rust
// K はキー毎の状態の置き場所。ファームは [KeyState; TOTAL_QT_KEYS]、PC は Vec<KeyState>
pub struct TouchSignal<K> { pub params: Params, /* ... */ }

impl<K: AsRef<[KeyState]> + AsMut<[KeyState]>> TouchSignal<K> {
    /// keys は全キー分の KeyState::INITIAL で埋めて渡す
    pub fn new(keys: K, params: Params) -> Self;

    /// 1 回分を処理する
    /// - now_us: 時刻（µs、u32。一周は wrapping_sub で扱う）
    /// - raw: キー毎の生値
    /// - valid: 読み取り成功フラグ（1 bit / キー）。失敗したキーはフィルタ履歴にも基準値にも反映しない
    /// - calibrating: 設定画面にいるか（SETTING_MODE）
    pub fn process(&mut self, now_us: u32, raw: &[u16], valid: u128, calibrating: bool);

    pub fn state(&self) -> State;          // Acquiring / Running / Calibrating
    pub fn keys(&self) -> &[KeyState];      // 結果: output()・filtered()・baseline()・delta()・noise_floor()
}
```

`process()` の中の処理の流れは次のとおり。

1. 読み取りに成功したキーだけ、ノイズ除去をかけて filtered を更新する（§3.3）
2. `calibrating` の立ち上がり・立ち下がりを検出して、状態を切り替える（§3.7）
3. 近傍の静かさ・大きく負の継続・固着を、全キー分判定する（§3.6, §3.7）。判定と更新を分けるのは、更新済みのキーの値で近傍判定がぶれないようにするため
4. 前回の更新から `BASELINE_UPDATE_INTERVAL_MS` 以上たっていれば、状態に応じて基準値を更新する
    - Acquiring: 積算する（§3.5）
    - Running: R1–R5、または固着からの回復（§3.6, §3.7）
    - Calibrating: 速い追従とノイズの計測（§3.7）
5. delta と output を計算する（§3.7）

### 4.4 `touch_task`

- `TouchSignal<[KeyState; TOTAL_QT_KEYS]>` を `touch_task` の中に持つ（タスクの future は静的に確保されるので、スタックは使わない。96 キーで数 KB）
- **`process()` を呼ぶ周期**: 解析（`QubitTouch`）と同じ、`analysis_divider()` フレームに 1 回（約 10ms 毎）とする（2026-10-03 決定）。§3.11 のパラメータ（移動平均のサンプル数など）は 8〜10ms 周期を前提にしているため。通常の構成ではスキャンが 10ms なので毎スキャンになる。`debug_stream`（スキャン 2ms）では 5 スキャンに 1 回になり、PC で間引いて見ていたのと同じ扱いになる
- **起動直後**: `TOUCH_STARTUP_SETTLE_MS`（500ms）の間は `process()` も呼ばない（2026-10-03 決定）。チップ自身の起動時の校正（230ms 未満）が終わる前の値で初期取得しないため。500ms の後、`ACQUIRE_MS` の初期取得が終わるまで output は 0
- `calibrating` には `SETTING_MODE` を渡す
- 各キーの `output()` を、従来どおり `QubitTouch::set_value()` で渡す
- `POINT0`–`POINT5`（OLED の表示）には、キー 0〜5 の output を出す（2026-10-03 決定。演奏の確認に分かりやすいため）
- 毎フレームの解析（フレーム駆動）と、`QubitTouch` の時間基準化は、速さ検出の設計で扱う

### 4.6 `src/touch/qtouch.rs`

## 7. 未決事項

- **1 周のスキャン時間**: 96 キーで実測してから、スキャン周期（`SCAN_PERIOD_US`）を 8ms にするか 10ms にするかを決める（§3.2）。10ms にすると、チップの 8ms 周期とずれて、ときどきサンプルを 1 つ飛ばす（`hw96_check.md` §2）
- **平滑化の強さ**: `SMOOTH_SAMPLES` を 2 にするか 4 にするか。ノイズの実測を見て決める
- **AVE の変更**: チップの AVE を 8 → 16 / 32 に上げて S/N を稼ぐか。その場合、OVERFLOW ビットを確認して 8ms に収まるかを見る。→ チップの境目のキーだけ上げる案を §3.12 で先に試す（2026-10-27）
- **近傍単位の追従による偏り**: ほぼ常にどこかが触れられている演奏では、触れられていない範囲だけが追従する。リング全体が一様に温度変化する場合、演奏中の指の周辺だけ基準値が遅れる。これを問題とみなすかどうかは実機で判断する
- **固着回復の適用範囲**: Violin モードでも有効にするか（§3.7）
- **noise_floor の保存**: 電源を切っても残すか（フラッシュへの保存）。今回の範囲には含めない → 保存せず、起動時に自動で測ることにした（§3.12、2026-10-29）
- **速さ検出の設計**: `QubitTouch` の側で計測する（§1.4 方針 4）。計測のしかた、ベロシティへの変換、Note On の遅延との兼ね合いは、別の設計書で扱う
