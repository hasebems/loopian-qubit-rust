# 96 キーのハードウェアへのファーム対応 設計書

- ハードの 2 回目の改修（`hw_modify.md` §8）に合わせたファームの変更を書く。決めた経緯は `hw96_check.md` §2.2
- **ハードが完成してから始める**（2026-11-14 決定）。それまではファームは今のまま（OLED を I2C0、スイッチを GP2・GP4）で調整を進める
- 改修後の基板と今のファームは組み合わせられない（逆も同じ。`hw_modify.md` §8.5）

## 1. 変更の概要

| 機能 | 今 | 変更後 | 使うタスク（コア） |
|---|---|---|---|
| I2C0 (400kHz) | OLED。SDA=GP0, SCL=GP1 | **センサー**（PCA9544 2 台）。ピンは同じ | `touch_task`（Core1） |
| I2C1 (400kHz) | センサー（PCA9544 4 台）。SDA=GP6, SCL=GP7 | センサー（PCA9544 2 台） | `touch_task`（Core1） |
| PIO の I2C (400kHz) | 無し | **SDA=GP3, SCL=GP4**。SSD1306 (0x3C)・PCF8574 (0x20) | `ui_task`（Core0） |
| スイッチ | GP2（右）・GP4（左）、内蔵プルアップ、Low で押下 | **PCF8574 の P0（左）・P1（右）**、Low で押下 | `ui_task`（Core0） |
| GP2 | スイッチ（右） | 使わない（予備） | |

- コアとタスクの分け方は変えない（`task_architecture.md`）。Core1 はタッチだけ、Core0 は入出力
- OLED とスイッチは `ui_task` が、PIO の I2C を専有して順番に使う。センサーの 2 系統は `touch_task` が専有する。どのバスも 1 つのタスクだけが使うので、バスの取り合い（ロック）は要らない

## 2. 進め方

ハードの改修が終わったら、次の順に進める。段階毎に、実機で確かめてからコミットする。

| 段階 | 内容 | 実機で確かめること |
|---|---|---|
| 1 | PIO の I2C（§3）と、OLED をそこへ移す | OLED に起動画面が出る。エラー 42・43 が出ない。診断ページの `Drw` が今と同じくらい |
| 2 | PCF8574 とスイッチ（§4） | 左右のスイッチでページが巡回する。同時押しで設定画面に入り、右で抜ける。エラー 52 が出ない |
| 3 | センサーの 2 系統化（§5） | 96 キーが読める（qubit_etude で全キーの raw が出る）。エラー 12 が出ない。`SCAN_TIME` が平均 10ms 前後 |
| 4 | 診断をバス毎に分ける（§7） | I2C 診断ページ（page 6）で 2 系統の時間と失敗の回数が見える |

- 段階 1・2 は I2C1 のセンサーのままでも確かめられる。センサーを I2C0 に足す前でもよい
- 段階 3 のキー番号の割り当て（§5.3）は、配線が決まってから決める

## 3. PIO の I2C

### 3.1 作るもの

- `src/devices/pio_i2c.rs`（仮）に、PIO で動く I2C のマスターを作る。embassy-rp の `pio_programs` には I2C が無い（ws2812 などしか無い）
- **embedded-hal-async の `I2c` trait を実装する**（`transaction` に Read・Write の両方）。`devices/ssd1306.rs` と新しい `devices/pcf8574.rs` は `&mut I2C`（この trait）を借りる作りなので、ドライバの側は PIO かどうかを知らなくてよい。`Oled::init` / `flush_buffer` はそのまま使える
- エラーの型は `embedded_hal::i2c::Error` を実装し、NACK（`NoAcknowledge`）とそれ以外（`Bus`・`Other`）を区別する

### 3.2 PIO のプログラム

- pico-examples の `pio/i2c/i2c.pio` と `pio_i2c.c` を移す。読み書き・ACK/NACK の検出・クロックストレッチに対応している
- `i2c.pio` は、クロックストレッチを待つ命令（`wait 1 pin, 1`）で、SCL が SDA の隣（SDA + 1）にあることを前提にしている。**SDA=GP3・SCL=GP4 はこの前提に合うので、命令はそのまま使える**（ピンをこう決めた理由。`hw96_check.md` §2.2）
- 仕組み（pico-examples と同じ）:
    - TX FIFO に 16 ビットの語を入れる。1 バイトの送受信（データ 8 ビット＋最後のバイトか・ACK を返すか）と、START・STOP・repeated START を作るための命令の差し込みの 2 種類がある
    - 読み込みのバイトは RX FIFO に入る
    - NACK を受けると、プログラムが IRQ を立てて止まる。ドライバはそれを見てエラーにし、ステートマシン（SM）を初期化し直す
- 分周比は、ビット 1 つの PIO のサイクル数と `clk_sys` から 400kHz になるように決める（pico-examples の計算と同じ）
- プログラムは embassy-rp が再公開している `pio` の `pio_asm!` で書く（`.pio` ファイルを別に置かない）

### 3.3 PIO の資源

- **PIO1 の SM0 を使う**。PIO0 は NeoPixel（SM0）が使っていて、`Common<PIO0>` は `ringled_task` に渡してしまうので、後から PIO0 に別のプログラムを載せにくい。I2C のプログラムは 30 命令前後あり、PIO の命令メモリ（32 語）の大半を使うので、別の PIO に置くほうが素直
- `bind_interrupts!` に `PIO1_IRQ_0 => PioInterruptHandler<PIO1>` を足す
- `main.rs`（Core0）で生成して `ui_task` に渡す。PIO の割り込みは Core0 で処理される（`ui_task` も Core0 なのでよい）
- ピンは PIN_3（SDA）・PIN_4（SCL）。外付けのプルアップを前提にし、内蔵プルアップも有効にしておく（補助。400kHz では内蔵だけには頼らない）
- RP2350 は PIO を 3 つ持つ（PIO0〜2）ので、PIO1 を使っても PIO2 が残る

### 3.4 非同期の待ち方

- FIFO への出し入れは embassy-rp の `StateMachineTx::wait_push` / `StateMachineRx::wait_pull` で待つ（割り込みで起きるので、CPU は回り続けない）
- NACK で SM が止まると FIFO が進まず、`wait_push` / `wait_pull` が終わらない。そこで、FIFO の待ちと NACK の IRQ の待ちを `select` で同時に待ち、IRQ が先に来たら NACK のエラーにする
- 1 画面（1024 バイト）の転送は今と同じく約 25ms。`ui_task` の `OLED_FLUSH_TIMEOUT_MS`（50ms）はそのまま使える

### 3.5 途中で打ち切られたときとバスの復帰

- `ui_task` はドライバの呼び出しを `with_timeout` で包むので、転送の途中で future が捨てられることがある。そのとき SM は転送の途中のまま止まり、スレーブが SDA を Low に保ったままのこともある
- そこでドライバは「転送中」のフラグを持つ。転送の初めに立て、正常に終わったら下ろす。**次の転送の初めにフラグが立ったままなら、先にバスの復帰を行う**。NACK・バスのエラーのときも、エラーを返す前に復帰を行う
- バスの復帰:
    1. SM を止め、FIFO を空にする
    2. SM に命令を直接実行（exec）させて、SDA を離したまま SCL を 9 回動かす（スレーブが送りかけのバイトを最後まで出させ、SDA を離させる）
    3. STOP を出す
    4. SM を初期化し直して動かす
- 復帰には数十 µs しかかからない。NACK だけ（デバイスが無いなど）のときは、バスは固まっていないので復帰は要らないが、場合分けを減らすため同じ処理を通す
- 起動時（最初の転送の前）にも 1 回、復帰を行う。リセットの直前に転送の途中だったスレーブがあっても、バスを使える状態から始める

## 4. PCF8574 とスイッチ

### 4.1 ドライバ

- `src/devices/pcf8574.rs` を足す。他のドライバと同じく I2C を所有せず、呼び出し毎に `&mut I2C` を借りる
- アドレスは **0x20**（7 ビット。A2〜A0 をすべて GND。TI のデータシートの 8 ビットの書き方では 0x40/0x41）
- PCF8574 にはレジスタが無い
    - `init`: 0xFF を 1 バイト書く（全ピンを入力にする。電源投入時も 0xFF だが、念のため書く）
    - `read`: 1 バイト読む。ビット n が Pn の状態
- 1 回の読み込みは、アドレス＋データで約 0.05ms（400kHz）

### 4.2 スイッチの判定

- ビットの割り当て: **P0 = 左、P1 = 右**。Low（0）で押下。定数で持つ（`SWITCH_L_BIT` = 0、`SWITCH_R_BIT` = 1。`tasks/ui.rs` か `constants.rs`）
- `ui_task` の 100ms 毎の判定で、今の `switch1.is_low()`（右）・`switch2.is_low()`（左）の代わりに PCF8574 を 1 回読み、2 つのビットから右・左を取り出す。その後の判定（押した瞬間の検出、同時押しで設定画面、右で抜ける）は変えない
- 読み込みは OLED の転送と同じバスで、同じ `ui_task` の中で順番に行うので、取り合いは起きない。OLED の転送中（約 25ms）はスイッチを読めないが、判定は 100ms 毎なので問題ない
- 読み込みは `with_timeout` で包む（`SWITCH_READ_TIMEOUT_MS` = 5ms 程度。1 回の読み込みは 0.05ms）
- 起動時は OLED の初期化の後に `init` する

### 4.3 読めなかったとき

- 初期化・読み込みの失敗（タイムアウトを含む）は、エラー 52（§6）を記録する
- **読めなかった回は、スイッチを前回の状態のままとする**（押した瞬間を作らない）。「押されていない」とすると、押し続けているスイッチが、読めるようになった回に押し直したように見えて、ページが勝手に変わるため
- 失敗した後は、PIO の I2C のドライバが次の転送の前にバスの復帰を行う（§3.5）。読めるようになれば、そのまま判定を続ける
- このバスが固まり続けると、OLED もスイッチも使えない（同時押しの設定画面にも入れない）。そのときはエラーの点滅（52・43）で分かる

## 5. センサーの 2 系統化

### 5.1 I2C の生成

- I2C0 も、I2C1 と同じく **Core1 の中で `I2c::new_async` する**。embassy-rp は `new_async` を呼んだコアの NVIC で割り込みを有効にするので、こうすると I2C0 の割り込みも Core1 で処理される
- `main.rs` は、`p.I2C0`・`p.PIN_1`（SCL）・`p.PIN_0`（SDA）を、今の I2C1 と同じく Core1 のクロージャに渡す
- `touch_task(i2c0, i2c1)` の 2 つを受け取る
- `Irqs` の `I2C0_IRQ` はすでに束ねてある

### 5.2 同時に読む

- 2 系統を `embassy_futures::join` で同時に読む。I2C の待ちは割り込みで起きるので、1 つのタスクの中で 2 系統の通信が並んで進む（`hw96_check.md` §2.1）
- `ReadTouch` のスキャンを、バス 1 系統分を読む関数（`scan_bus`）に分ける。I2C の型（`I2c<I2C0>` と `I2c<I2C1>`）が違うので、`embedded_hal_async::i2c::I2c` を取る総称型の関数にする（`devices` のドライバはすでに総称型）
- 生値の配列 `raw_value` を、`split_at_mut` でバス毎の範囲に分けて、それぞれの `scan_bus` に渡す。読み取り成功のフラグは、バス毎に返して、`join` の後でまとめる。配列を新しく持たないので、メモリは増えない
- `scan_bus` の中身（PCA9544 の ch の選択 → AT42QT1070 の 6 キーの読み取り → hi/lo ずれの読み直し → 最後の ch の後に切断）は今の `touch_sensor_scan` と同じ。タイムアウトも今と同じく通信 1 回毎にかけるので、片方のバスが固まっても、もう片方は読み続ける
- 初期化（`init_touch_sensors`）もバス毎に分け、`join` で同時に行う。各バスは 8ch なので、`TOUCH_INIT_TIMEOUT_MS`（150ms）は今のままで足りる
- `At42Qt1070` と `Pca9544` は状態を持たない（アドレスだけ）ので、2 つの future で共有して借りられる。`At42Qt1070` の関数が `&mut self` を取っているところは `&self` に直す（または各バスに 1 つ持つ）

### 5.3 構成とキー番号

- バス毎の構成を `constants.rs` に定数の表で持つ:
    - PCA9544 の台数・ch 数・アドレス
    - そのバスの最初のキー番号（バス 0 のキーが先、バス 1 のキーが後に続く）
- `Pca9544` は、今は `0x70 + dev` でアドレスを決めている。アドレスを引数で受け取るように変える（各バスで 0x70・0x71 を使うか、0x70〜0x73 を分けるかは基板で決める。`hw96_check.md` §2.2 の未決）
- 構成毎の表:

| 構成 | I2C0 | I2C1 | キー数 |
|---|---|---|---|
| 本番（feature 無し） | PCA9544 2 台 × 4ch | PCA9544 2 台 × 4ch | 96 |
| `etude` | 使わない（0 台） | PCA9544 1 台 × 2ch | 12 |
| `no_pca9544` | 使わない（0 台） | AT42QT1070 1 個を直結 | 6 |

- `etude`・`no_pca9544` では I2C0 にセンサーが無い。I2C0 は生成するが、台数 0 のバスの `scan_bus` はすぐに終わる。`TOTAL_CH`・`TOTAL_QT_KEYS` は表から計算する
- **キー番号の割り当ては仮に「バス 0 の ch 順 → バス 1 の ch 順」とする**。リングの並びと配線の向きが決まったら、表（最初のキー番号）と `CH_CONVERSION`（バス毎に持つ）で合わせる。範囲がバス毎に続かない割り当て（交互など）が必要になったら、`raw()` で並べ替える
- リングのつなぎ目（キー 95 → 0）は `touch_algo` が扱う（`TOUCH_RING`）ので、どこをキー 0 にしても動く

### 5.4 時間の見込み

- 1 系統 8 チップで、スキャンは平均約 10ms、最悪約 12ms（`hw96_check.md` §2.1）
- `SCAN_PERIOD_US` は 10ms のまま。周期を超えた回は今と同じく `PERIOD_OVERRUN` を数えて `ticker.reset()` する
- `touch_algo` の時間は実時間で数える（`touch_analysis.md` §3.8）ので、解析の間隔が 10〜12ms に延びても時間の感覚はずれない
- `debug_stream` の 2ms の周期では、スキャンが周期に収まらず毎回 `PERIOD_OVERRUN` になる。96 キーでの観察は 10ms か 20ms で行う（PC の `period` コマンド）

## 6. エラーコード

| コード | 名前 | 意味 | 変更 |
|---|---|---|---|
| 42 | `OLED_INIT` | OLED の初期化エラー | 変えない（PIO の I2C での失敗） |
| 43 | `OLED_FLUSH` | OLED の転送エラー（タイムアウトを含む） | 変えない（同上） |
| **52** | `SWITCH_READ` | **スイッチ（PCF8574）の初期化・読み込みのエラー（タイムアウトを含む）** | 新しく足す |
| 12 | `TOUCH_INIT_TIMEOUT` | タッチセンサの初期化の失敗 | 変えない（2 系統のどちらかで失敗したら） |

- 52 にした理由: 表示の 4x は 41〜45 が埋まっている。スイッチは設定画面（エラーのクリア・校正）に入るためのもので、システムの操作に近い。5x は 51（`SPAWN_STATUS_LED`）と 55（`PANIC`）だけで、52〜54 が空いている
- `error.rs` の 5x の見出しのコメントを「システム（スイッチを含む）」にする
- PIO の I2C のバスの復帰（§3.5）は、エラーコードにしない（42・43・52 のどれかが先に記録されるため）。回数は診断値で数える（§7）

## 7. 診断

- `SCAN_TIME` はスキャン全体（`join` の全体、つまり 2 系統の長いほう）。今と同じ
- I2C 診断ページ（page 6）の値を **バス毎に分ける**。片方のバスだけが遅い・失敗するのを見分けるため
    - `shared.rs` の `I2C_SELECT_TIME`・`I2C_READ_TIME`・`I2C_DISCONNECT_TIME`・`I2C_REREAD_COUNT`・`I2C_FAIL_COUNT` を、バス毎の配列（`[TimeStat; 2]` など）にする
    - 表示は、行（Sel・Rd・Dis・再読・失敗）毎に 2 系統を並べる。画面の幅（6×10 のフォントで 21 文字）に収めるため、時間は平均と最大だけにする（例: `Rd  1100 1350|1098 1342`）
- `join` の中で 2 系統が並んで進むので、通信 1 回の時間には、もう一方のバスの割り込みの処理の分が少し混ざる。1 系統のときより少し長めに出ることがある
- PIO の I2C のバスの復帰の回数（`OLED_BUS_RECOVERY_COUNT`、仮）を足し、page 6 か診断ページ（page 5）に出す
- 診断値のクリア（`reset_diagnostics`、設定画面に入ったとき）にも足す
