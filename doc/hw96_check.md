# 96 キーの新ハードウェアでの確認項目

96 キーの新しいハードウェアができてから確かめることをまとめる（2026-10-18 作成）。それまでは 6 キー直結の構成（2026-10-24 からは `etude` の 12 キー構成も）で開発を進め、ここに挙げた項目は新しいハードウェアで行う。各項目の詳しい内容は、それぞれの元の設計書の節に書いてある。この書類は一覧と、結果を書き込む場所とする。

## 1. ファームに適用した後の実機確認（F1〜F6）

元: `touch_baseline.md` §6.2、`debug_env.md` §6.2.1 の段階 2 の 2

チップの基準値を `touch_algo` に置き換えた後（`debug_env.md` §6.1 の段階 4、2026-10-03）の、演奏の結果（ノートの出方）での確認。

| # | シナリオ | 期待する結果 | 結果 |
|---|---|---|---|
| F1 | 何も触れずに起動し、数分放置 | ゴーストノートが出ない | |
| F2 | 通常の演奏（スライド・複数点・素早い連打） | 反応が従来と同等以上。演奏中に感度が落ちていかない | |
| F3 | Violin モードで 30 秒以上ロングトーン | 途中で音が切れない（固着と誤判定されない） | |
| F4 | パッドに導電性の物を載せたまま放置 | `STUCK_TIME_MS` 後に回復が始まり、ノートが止まる | |
| F5 | 約 1 秒かけてゆっくり指を近づける | 基準値が吸収して発音しない、ということが起きない | |
| F6 | 設定画面に入って数秒待ち、出る | 無操作時のちらつき（OLED の POINT 表示）が減る。反応の遅れが体感で増えない | |

- `TOUCH_THRESHOLD` と追従のパラメータは、必要なら実際に演奏して調整する（`touch_baseline.md` §5）
- 期待する結果を変えるときは、`touch_baseline.md` §6.2 も合わせて直す

## 2. スキャンの周期と周期超過

元: `debug_env.md` §8、`touch_baseline.md` §7 の「1 周のスキャン時間」

演奏に使うのは 96 キーの構成なので、処理時間（パフォーマンス）は 96 キーで考える。6 キーの構成で 2ms 周期の間隔を確かめること（`debug_env.md` §8）は行わない（2026-10-18 決定）。96 キーでは 1 周のスキャンに 8ms 前後かかる見積もりで、2ms の周期にはそもそも収まらないため。それまでのタッチ処理の設計は、10ms 程度の時間分解能を前提にする（`debug_env.md` §6.2.4）。

- 1 周のスキャン時間を診断ページの `SCAN_TIME`（最小・平均・最大）で実測し、スキャン周期（`SCAN_PERIOD_US`）を 8ms にするか 10ms にするかを決める（`touch_baseline.md` §3.2）。10ms にすると、チップの 8ms 周期とずれて、ときどきサンプルを 1 つ飛ばす
- 決めた周期で `PERIOD_OVERRUN` が増えないこと。スキャン＋解析が周期を超えることが常態化するなら、`task_architecture.md` §4.1 のとおりタスクを分けるなどの対処を考える

## 3. キー毎の感度がそろっているか

元: `debug_env.md` §6.2.3 の「96 キーでの再確認」

キー毎の感度の補正（キャリブレーション）は、6 キーでの観察から中止した（2026-10-18）。その判断はチップ 1 個・6 キーでのものなので、96 キーでも成り立つかを確かめる。

- 触らずに全キーの raw を並べる。チップ同士の差があれば、6 キー毎の段差として現れる
- 普通に触ったときの delta もざっと見て、キー同士で同じくらいに収まっているか（6 キーでは 80〜100 くらい）
- 差が大きければ、そのときに改めて対応を考える

## 4. 空のチャネルの後のチャネルが読めない（解決: 接触不良と思われる）

元: 2026-10-25、`etude`（PCA9544 1 台 × 2ch）でチップを 1 個だけつないで試したときに見つかった。`etude` の目的（動作仕様を決める）とは別の問題なので、ここで扱う。**`etude` で 12 キーが揃って動いた時点で、この項目を思い出して、次の「確かめること」の 1 を行う**

**症状**

- チップ（AT42QT1070）は 1 個だけ。同じチップ・同じコネクタを差し替えて試した
- ch 0 につなぐと key0〜5 は毎回読める（ch 1 は空）
- ch 1 につなぐと key6〜11 が 1 回も読めない（ch 0 は空）。PC に送るフレームの `valid` がすべて 0
- 配線・導通・プルアップ（抵抗値まで）は確認済み。部品は今までと同じ PCA9544

**仮説: 空のチャネルで NACK が出た直後の I2C の通信 1 回が、正しく行われていない**

| チップの位置 | NACK の後の I2C | 結果 |
|---|---|---|
| ch 0（動く） | ch 1 の読み取りで NACK → 切断（0x00）→ 次の周期の ch 0 の選択（0x04） | 失われるのが切断なので害が無い |
| ch 1（動かない） | ch 0 の読み取りで NACK → **ch 1 の選択（0x05）** → ch 1 の読み取り | 選択が失われ、PCA9544 が ch 0（空）のままになる |

- embassy-rp の I2C で、NACK による中断やストップ検出の状態が残り、次の書き込みが終わる前に完了扱いになる（続く読み取りの準備で打ち切られる）か、エラーになる、と推測している。確かめてはいない
- 本番（全チップあり）や `no_pca9544`（直結）では NACK がまず出ないので、これまで気づかなかった
- 本番でも、チップが 1 個壊れたり外れたりすると、次のチャネルまで読めなくなる。回路の不具合の調査が難しくなるので、最終版までに直す

**確かめること**

1. 2 セットそろえた `etude` で、key6〜11 も読めるか。読めれば仮説と合う（0x05 や ch 1 の配線は問題ない）。読めなければ仮説は外れで、ch 1 の経路を改めて調べる
2. 1 セットを外して症状を再現し、チャネル毎に「切り替え（`pca.select`）の失敗」と「読み取りの失敗」の回数を数えて PC に送る診断を入れ、ch 1 の選択が毎回失敗しているかを見る
3. 当たっていたら、読み取りに失敗した後の切り替えが失敗したときに、もう一度やり直すなどの対処を入れる

**結果（2026-10-25）**

- 1: 2 セットそろえた `etude` でも key6〜11 が出ない。ファームは `etude`（qubit_etude の表示で 12 キー）。key6〜11 は raw の線が描かれず、`valid` が 0（1 回も読めていない）。統計の表で raw 平均・p-p が 0 になるのは、読めたサンプルが無いため。チップを入れ替えても同じ（どちらのチップも ch 0 では動く）。全チップがあるので NACK は出ないはずで、**仮説は外れ**
- スキャンの順番を ch 1 → ch 0 に入れ替えた（`CH_CONVERSION` を `[1, 0, 2, 3]`）ところ、ch 0 のチップは 2 番目に読んでも読めた。読む順番ではなく ch 1 という場所の問題
- テスターでは ch 1 の経路の導通に問題が無かった。オシロでは、SC1・SD1 に周期的に少しだけ波形が出るが、読み取りに足りるほどのクロックは出ていなかった
- コネクタを何度も挿し直しているうちに、全チャネルが読めるようになった。**接触不良だったと思われる**。チップを 1 個だけ ch 1 につないだときの症状も、同じ原因だった可能性が高い
- 「空のチャネルで NACK が出た後の通信が失われる」は確かめていないが、この症状の説明には要らなくなった。チップが外れたときの振る舞いは、96 キーのハードウェアで改めて確かめる
