# 96 キーの新ハードウェアでの確認項目

96 キーの新しいハードウェアができてから確かめることをまとめる（2026-10-18 作成）。それまでは 6 キー直結の構成で開発を進め、ここに挙げた項目は新しいハードウェアで行う。各項目の詳しい内容は、それぞれの元の設計書の節に書いてある。この書類は一覧と、結果を書き込む場所とする。

## 1. ファームに適用した後の実機確認（F1〜F6）

元: `touch_baseline.md` §6.2、`debug_env.md` §6.2.1 の段階 2 の 2

チップの基準値を `touch_algo` に置き換えた後（`debug_env.md` §6.1 の段階 4、2026-10-03）の、演奏の結果（ノートの出方）での確認。

| # | シナリオ | 期待する結果 | 結果 |
|---|---|---|---|
| F1 | 何も触れずに起動し、数分放置 | ゴーストノートが出ない | |
| F2 | 通常の演奏（スライド・複数点・素早い連打） | 反応が従来と同等以上。演奏中に感度が落ちていかない | |
| F3 | Violin モードで 30 秒以上ロングトーン | 途中で音が切れない（固着と誤判定されない） | |
| F4 | パッドに導電性の物を載せたまま放置 | `STUCK_TIME_MS` 後に回復が始まり、ノートが止まる | |
| F5 | 約 1 秒かけてゆっくり指を近づける | 基準値が吸収して発音しない、ということが起きない | |
| F6 | 設定画面に入って数秒待ち、出る | 無操作時のちらつき（OLED の POINT 表示）が減る。反応の遅れが体感で増えない | |

- `TOUCH_THRESHOLD` と追従のパラメータは、必要なら実際に演奏して調整する（`touch_baseline.md` §5）
- 期待する結果を変えるときは、`touch_baseline.md` §6.2 も合わせて直す

## 2. スキャンの周期と周期超過

元: `debug_env.md` §8、`touch_baseline.md` §7 の「1 周のスキャン時間」

演奏に使うのは 96 キーの構成なので、処理時間（パフォーマンス）は 96 キーで考える。6 キーの構成で 2ms 周期の間隔を確かめること（`debug_env.md` §8）は行わない（2026-10-18 決定）。96 キーでは 1 周のスキャンに 8ms 前後かかる見積もりで、2ms の周期にはそもそも収まらないため。それまでのタッチ処理の設計は、10ms 程度の時間分解能を前提にする（`debug_env.md` §6.2.4）。

- 1 周のスキャン時間を診断ページの `SCAN_TIME`（最小・平均・最大）で実測し、スキャン周期（`SCAN_PERIOD_US`）を 8ms にするか 10ms にするかを決める（`touch_baseline.md` §3.2）。10ms にすると、チップの 8ms 周期とずれて、ときどきサンプルを 1 つ飛ばす
- 決めた周期で `PERIOD_OVERRUN` が増えないこと。スキャン＋解析が周期を超えることが常態化するなら、`task_architecture.md` §4.1 のとおりタスクを分けるなどの対処を考える

## 3. キー毎の感度がそろっているか

元: `debug_env.md` §6.2.3 の「96 キーでの再確認」

キー毎の感度の補正（キャリブレーション）は、6 キーでの観察から中止した（2026-10-18）。その判断はチップ 1 個・6 キーでのものなので、96 キーでも成り立つかを確かめる。

- 触らずに全キーの raw を並べる。チップ同士の差があれば、6 キー毎の段差として現れる
- 普通に触ったときの delta もざっと見て、キー同士で同じくらいに収まっているか（6 キーでは 80〜100 くらい）
- 差が大きければ、そのときに改めて対応を考える
